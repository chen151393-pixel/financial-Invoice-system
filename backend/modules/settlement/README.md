# settlement 模块：结汇对账

## 报关应收汇查询优化（2026-11-26）

报关应收汇通过 `DocumentReader.states(connection, contexts)` 批量读取提单、销售合同、来源、主体及归档状态；`contexts` 按香港批次 ID、直接收汇单号或 `DocumentGroupRef` 隔离。直接收汇资料组即使只命中部分列表成员，也读取完整组成员后判断资料状态。完整历史收汇推算、金额与资料齐全规则不变；不跨请求缓存，也不写主数据。专项验证见 `tests/test_navigation_query_performance.py`。

## 客户名称格式归并（2026-11-27）

应收客户汇总、收汇总览、直接收汇总账、逐单冲抵及流水解释共用 `policy/consignee_policy.py`：全半角统一后去除符号和空白、统一大写，只保留文字和数字后精确匹配。例如 `MECOLOUR DIGITAL TECHNOLOGY (HK) CO., LIMITED`、`Mecolour-Digital Technology/HK CO LIMITED.` 均归为 `MECOLOURDIGITALTECHNOLOGYHKCOLIMITED`。字母、数字或地区内容不同仍视为不同客户，不做相似度匹配。不同币种分别汇总；直接收汇冲抵仍严格区分收款抬头，不跨公司挪用到账金额。

香港公司名单匹配、候选组合、香港登记选单、资料组客户一致性校验及工作区筛选使用相同规则。合同买方抬头按此规则匹配，命中多个档案时提示核对，不自动选取地址或印章；卖方抬头和收款公司的规则不变。名单 `SETTLEMENT_HK_CONSIGNEES` 仍须以英文分号分隔不同公司；公司名称自身的逗号不是分隔符。

展示优先使用 `SETTLEMENT_HK_CONSIGNEES` 中的原始写法；同一匹配键重复配置时取第一项。其他直接收汇客户使用 `settlement_consignees` 中已登记的原名：匹配键存在就归入已有客户，首次出现才新增，后续格式变体不覆盖原名。表以匹配键作为主键；海关回执通过 `CustomsReceiptsSaved` 事件、银行流水通过导入 Service 在同一事务内登记，唯一键冲突时保留已有名称。查询只读取一次名称快照，不写表、不使用跨请求可变缓存。

部署须先执行 `npm run db:upgrade`（新增 `0058_settlement_consignees`）。应用通过版本核验后、启动工作线程前，按现存回执、银行流水及批次中最早可用记录幂等补齐名称；同一时间按来源类型、记录 ID 确定顺序。此前已被覆盖且无历史记录的格式无法还原；已登记名称在后续启动和重导中保持不变。应收、总览、候选、逐单详情、资料组、香港登记与工作区、批次和银行流水响应统一展示口径；原始回执、冻结批次及银行流水名称不改写，合同正文仍使用维护的合同抬头。读取历史 `customer_key` 时使用同一匹配规则，银行导入去重摘要与三方代付标记保持原口径。修改 `.env` 后需重建应用容器以加载配置。专项测试见 `tests/settlement/test_consignee_identity.py`、`test_consignee_registry.py`；MySQL 并发专项需配置专用测试库，未配置时跳过。

## 职责

报关之后的结汇：客户货款必须与报关金额一致。按报关单“贸易国”分两条回款路径：

| 路径                  | 判定                 | 资金流                     | 对账                                                                                 |
| --------------------- | -------------------- | -------------------------- | ------------------------------------------------------------------------------------ |
| `hk_transit` 香港中转 | 贸易国为中国香港     | 客户 → 香港账户 → 汇回境内 | 两段：香港到账对报关合计；汇回境内对报关合计。批次与汇回一一对应（按资料一单一单做） |
| `direct` 直接收汇     | 贸易国为真实客户国家 | 客户 → 境内账户            | 总账：按境外收货人、收款人和币种汇总，出口加、收汇减，不建批次                                 |

**香港中转——差额只认手续费**：到账金额 + 手续费 = 报关合计，严格相等才通过；手续费超过 `SETTLEMENT_FEE_ALERT` 时提示复核，防止把少收款当作手续费。登记回款建批次、汇回结汇适用于香港中转；提单与销售合同也支持直接收汇，按报关单独立保存。

**直接收汇——总账（2026-11-18 业务确认）**：非香港中转的报关单不建批次，进入“直接收汇明细”。按境外收货人、收款人和币种汇总期初、本期出口、本期收汇和期末差额，同一天的流水先展示出口；余额为正是未收，为负是超收。出口取海关回执的出口日期与成交总价，出口抬头取 NS 报关单的申报主体；收汇取银行收汇明细，按表格中填写的实际客户归到收货人。付款人户名与实际客户不同即三方代付，只作标记，不影响归属，也不判断是否有代付协议。香港公司汇回境内的款项不进总账。金额或币制有问题、没有境外收货人的直接收汇报关单不计入总账，在页面上单独列出原因。

> 海关回执导入文件目前不含“贸易国”。未取得贸易国时，按境外收货人是否为集团香港公司判定（`SETTLEMENT_HK_CONSIGNEES`，分号分隔；为空时使用 `policy/route_policy.py` 内置名单）。NS 报关记录字段 `custrecord_swc_country_body`（值 95 为中国香港）同步进 source 后，可直接传入 `route_of()` 的 `trade_country`。

## 拥有的表

- `settlement_consignees`：规范化匹配键与首次登记名称；香港显示由环境配置覆盖，后续格式变体不新增客户、不覆盖已有原名。

直接收汇明细按境外收货人、收款抬头及币种对账。选择起止日时，开始日前的出口与到账累计差额为期初，起止日当天计入本期。出口使用海关回执出口日期，收汇使用银行实际入账日期。选择期间时，缺出口日期的报关单单独提示。

总账按报关金额和实际到账金额汇总。展开可查原始流水、来源单据编号及每笔后的余额，从期初差额起按时间顺序加出口、减收汇。

- `settlement_batches`：结汇批次（一笔回款），含到账、手续费、汇回、状态与经办人。
- `settlement_batch_items`：批次包含的报关单，建批次时冻结海关回执成交总价；`active_declaration_no` 唯一约束保证同一报关单只在一个有效批次中，作废后释放。

- `settlement_bills`：香港批次或直接收汇报关单的提单文件及提单号、装运口岸、目的口岸、装船日期、对应的报关单；移除为软删除。
- `settlement_contracts`：按模板生成的销售合同 PDF（各资料范围内按出口合同号一份）及生成依据摘要。
- `settlement_parties`：销售合同买卖双方抬头（中英文名称、地址、电话）与印章图片。
- `settlement_bank_receipts`：银行收汇明细（收汇日期、收汇抬头、付款人户名、实际客户、币种、金额、流水号）；规范化名称 `customer_key` 用于归属境外收货人，`payer_key` 与它不同即三方代付。

文件本体（提单、合同 PDF、印章图片）保存在 `SETTLEMENT_DOCUMENT_ROOT`，只用服务端 UUID 命名，数据库记录标识与校验值；部署时该目录须为持久卷。

结汇迁移见[表与迁移对照](../../../docs/mysql/schema-map.md#settlement)。已有银行流水允许交易时间和导入去重摘要为空。

## 银行流水导入

2026-11-19 汇总卡片：银行收汇按收款抬头全称分别汇总上海绎色数码科技有限公司、上海绎视数码科技有限公司、上海毅鑫实业有限公司，名称规范化后全称一致才合并，不按付款方、实际客户或账套编号分组。三个主体在当前筛选范围内无记录时补零；其他抬头保留汇总并单独展示。按币种分别统计，无任何流水时展示三张 USD 零值卡片。`totals[].featuredCompany` 标识三个指定抬头，合计覆盖全部筛选结果，不受分页影响。

- 支持银行导出的 .xlsx，按双语表头中的中文列名识别，只保存「来账」。境外收货人名称为实际客户。
- 按银行流水号或原始交易字段识别重复记录。缺少流水号及交易时间时，按原文件和行号识别重传。同一笔流水的客户、付款人或金额冲突时，提示行号并回滚本次导入。
- 每笔保存来源文件名、Excel 行号和导入人，导入结果列出新增、重复和跳过的笔数。

## 收汇总览（2026-11-19）

`POST /api/settlement/overview/query` 返回累计收汇概况和按境外收货人、路径、币种分组的明细，支持 `consignee`、`currency`、`page`、`pageSize`；权限沿用 `settlement`，只读，无新增表或迁移。

报关应收汇接口另返回 `combinedTotals`：在当前筛选范围内，将香港中转和直接收汇按币种合计，原始 Decimal 加总后再格式化；与路径分项采用相同筛选，不受最多列出 500 张明细的限制。

- 应收取已关联 NS 报关单的当前海关回执有效成交总价；金额、币制有问题或缺收货人的报关单不计入，并在 `skipped` 返回原因。已建批次的报关单仍计入应收。
- 香港客户实收取未作废香港批次的 `received_amount`，包括已收款、资料已出和已结汇批次；只计首次客户到账，不叠加 `remitted_amount` 或银行明细中的香港汇回。旧直接收汇批次不作为新总览的实收来源。
- 直接收汇实收与直接收汇总账同源，取银行流水中实际客户判定为直接收汇的金额；有实收但尚无报关应收的预收客户也单独列出。
- 未收金额严格为应收减客户实收，不截断负数（超收），不把“未建批次”当作未收。手续费单列，不计入客户实收，因此未收差额中仍包含手续费。
- 不同币种分别统计，不折算相加；合计覆盖全部筛选结果，不受分页影响。总览不判断单笔订单收齐，不改变资料、汇回或结汇状态。仅反映已登记数据，不能代表未登记的香港银行到账。

## 报关应收汇逐单状态（2026-11-20）

`POST /api/settlement/receivables/query` 只读，无新增表或迁移。规则在 `policy/receivable_policy.py`，读取与汇总在 `service/receivable_service.py`：

- **已收**：香港中转取所在有效批次的“到账 + 手续费”，按出口日期先后冲抵批次内报关单的冻结金额；未建批次为 0。直接收汇不分配到单，按“同一境外收货人、同一收款抬头（报关单 NS 申报抬头 = 银行收款抬头）、同一币种，先出口的先冲抵”推算，口径与直接收汇明细按收款抬头拆分一致；冲抵后剩余为超收。推算始终基于全部历史，查询条件只筛选展示结果。
- **结汇阶段**：香港中转按批次状态——待登记回款 / 香港已收·办资料 / 资料已出·待汇回 / 已结汇；直接收汇按推算已收——未收汇 / 部分收汇 / 已结汇（收齐即结汇）；金额、币制或收货人缺失为“数据待处理”。
- **账龄**：未结汇报关单自出口日至今天（Asia/Shanghai）的天数。香港资料已出后，自到账日超过 30 天未汇回提示“香港滞留 N 天”。
- **资料状态**：香港中转资料挂在批次下，只对“香港已收”批次读取资料清单（未建批次显示“登记回款后办理”，资料已出后显示“资料已出”）；直接收汇只对已上传提单或已生成合同的报关单读取资料现状，没有资料显示“未办理”，资料状态不影响结汇阶段。
- **注意**：这里的已收含手续费（客户实付），收汇总览的“客户实收”只计到账金额、手续费单列，两处未收可能相差手续费。

## 批次状态

```text
香港中转：collected 香港已收 → documents_ready 资料已出 → settled 已结汇（汇回对平）
未结汇前均可 cancelled 作废，作废释放报关单。
```

直接收汇不再建批次。此前已建的直接收汇批次（`collected 已收款 → settled 已结汇`）仍可结汇或作废：`BatchService.settle()` 与 `batch_state_policy` 中的 `DIRECT` 转换只为这些旧数据保留，调用方是批次详情的“确认结汇”；页面已不再列出直接收汇批次。确认库中没有未完结的直接收汇批次后（核对语句见手动执行脚本）一并删除。

状态转换集中在 `policy/batch_state_policy.py`；可操作判断（`allowed/reason`）由后端返回，执行时再次校验。

## 结汇资料（香港中转）

香港中转批次在“香港已收”阶段准备资料，**提单与销售合同齐全后才能确认资料已出**；确认后资料只读，仍可下载。

- **提单**：上传 PDF（单个不超过 8 MB）。有文字层的提单由 `policy/bill_parse_policy.py` 从文字中识别提单号、装运口岸、目的口岸、装船日期。**扫描件**（无文字层）由 `service/bill_ocr.py` 取第一页图像、去掉彩色底纹后调用本机 tesseract，`policy/bill_layout_policy.py` 按“标签下方 / 右侧同一栏”的位置取值；同一页用两种方式各识别一次，**结果一致的字段才采用**，装船日期的数字写法与英文序数写法（OBD）不一致时不取。识别不到的留空由人工填写，不猜测港口。扫描识别可能认错字符（如 0 与 O），识别出的提单标“待核对”，经办人对照原件点“修改”保存后提示消除。未安装 tesseract 或 `SETTLEMENT_OCR_COMMAND` 留空时，扫描件字段全部人工填写。可选的识别模型补空见下文“提单识别模型”。每张提单标明对应的报关单（默认批次内全部）。
- **销售合同（即形式发票，2026-11-18 业务确认）**：按 `templates/sales_contract.json`（由原人工模板整理的版式与条款）生成 PDF，批次内每个出口合同号一份。明细与金额取海关回执成交总价，单价 = 成交总价 ÷ 成交数量（仅展示）；签订日期 = 最早出口日期往前推 `SETTLEMENT_CONTRACT_LEAD_DAYS` 天（默认 28）；装运口岸、目的口岸取对应提单；买方按对应报关单的当前境外收货人匹配合同抬头，卖方按对应 NS 报关单的申报抬头匹配；成交方式和付款条件由经办人确认。双方印章取合同抬头的印章图片，缺印章时照常生成并提示。
- **需重新生成**：提单口岸、海关回执明细、合同抬头或印章变化后，已生成合同的依据摘要不再一致，须重新生成才算齐全。海关回执换版导致合计与建批次时不一致时，须作废批次重建。
- **报关单**：取 task 模块从 NS 下载并归档到共享盘的报关单原件（`task/public.py` 的 `archived_declaration_files`，只读），按原件格式（PDF 或 NS 打印模板的 xls）放入资料包，不转换格式；读取时核对归档校验值且路径须在共享盘目录内。**未归档只提示、不阻止确认资料已出**，需到“开票跟进”的任务详情下载。结汇模块自身不下载、不改归档记录。
- **资料包**：齐全后可下载 zip，结构为“批次 / 出口合同号 / 销售合同（形式发票）、提单、报关单”，附文件清单；未能放入的报关单在清单中注明原因。
- 中文字体：默认使用 PDF 内置 STSong-Light（不嵌入，英文数字用 Helvetica）；配置 `SETTLEMENT_PDF_FONT`（TTF 路径）后改为嵌入该字体。

### 合同双方自动匹配（2026-11-19）

香港与直接资料统一按每份出口合同的关联报关单确定双方：买方取当前海关回执的境外收货人，卖方取 NS 报关单的唯一申报抬头。地址、英文名称、电话和印章从同名合同抬头读取；不使用其他公司或最近使用卖方兜底。缺少当前来源、NS 重号、缺申报抬头、同一合同覆盖不同买方/卖方时禁止生成并给出缺项；不同出口合同可各自匹配不同申报公司。

资料响应的 `planned[]`、`contracts[]` 增加 `buyerName`、`sellerName`；生成表单只读展示双方。生成请求的 `sellerPartyId` 为可选兼容字段，旧客户端若传入必须与当前 NS 匹配结果一致。后端逐合同重新解析并在文件生成前后核对双方身份与生成摘要；买方、NS 申报抬头或主数据变化时旧合同提示重新生成。不自动修改既有合同文件，不改变收款和批次金额。专项测试见 `test_contract_parties.py`。


### 扫描提单识别补充（2026-11-19）

扫描件支持 `B/L No.` 与 `Bill of Lading No.` 标签；整页识别有歧义时，仅对两次均定位到同一提单号词框的区域放大复识，局部两次结果一致才采用。不以订舱号替代提单号，不猜测号码中的相似字符。装船日期允许标签同行留白，仅在明确的 `日-英文月份-年` 日期日字段修复 O/0，不取上方签发日期。两次仍有歧义的字段留空，并保留人工核对提示。已有上传记录不会因刷新自动重算；重复上传相同 PDF 会用最新解析结果补齐原记录的空字段，保留已有值、人工核对信息、文件及报关单关联，不创建重复提单。无可补齐字段时返回明确提示，仍可人工修改。专项回归见 `test_settlement_bill_ocr.py`。


扫描表格提单补充（2026-11-19）：整页港口或装船日期结果有歧义时，按实际横竖表格线定位栏位，将标签与值分开，对值区域放大并用两种方式复识；两次均能按原标签解析且一致才采用。横线小缺口不截断栏位，未定位到邻近表格线时放弃局部复识。日期标签与数值之间的宽留白不再当作新栏目；只在同一行完整日期格式匹配时取值，签发日期仍不能替代装船日期。表格装船日期即使整页两次结果一致也做局部复核，降低表格线使两次同时把 1 误读为 4 的风险。直接收汇和香港中转共用此实现。测试见 `test_settlement_bill_cells.py`，私有提单原件不纳入仓库。

### 提单识别模型（2026-11-24，可选，默认关闭）

`SETTLEMENT_BILL_RECOGNIZER` 决定提单识别方式，默认 `rules`：只用上面的本地规则（文字层解析 + tesseract），不调用任何模型，行为与此前一致。设为 `openai_compatible` 并填写 `SETTLEMENT_BILL_MODEL_BASE_URL`、`SETTLEMENT_BILL_MODEL_API_KEY`、`SETTLEMENT_BILL_MODEL_NAME` 后，本地规则**仍先执行**，只有还缺字段时才调用识别模型补空；换模型或换厂商只改这三项配置。扫描件按图片发送，须选支持图片输入的模型。

- 适配器：`backend/integrations/model_extraction.py`，对接 OpenAI 兼容接口（`POST {base_url}/chat/completions`，JSON 输出模式），只管传输；接口格式不同的厂商在该文件新增适配器并在 `create_extractor` 登记。目前只实现了 `openai_compatible` 一种。
- 输入：`service/bill_model_reader.py`。有文字层的提单发提取出的文字；扫描件发第一页彩色原图（长边不超过 2200 像素的 JPEG）。调用在数据库事务之外。
- 规则：`policy/bill_model_policy.py`。提示词要求认不出就留空；返回值逐字段校验（提单号 6–20 位字母数字且含数字、口岸不含数字与栏位标签、日期为合法的 `YYYY-MM-DD`），不合格的当作没识别到。合并时只补本地规则留空的字段；**两边都有值但不一致的字段留空**，说明中注明“不一致”。
- 提示：采用了模型值的提单说明中带“部分字段由识别模型给出，可能有误，请对照原件核对”，与扫描识别一样计入“待核对”，经办人保存后消除。
- 降级：模型超时、报错或返回格式不对时沿用本地规则的结果，上传不受影响；日志只记录状态，不记录密钥和提单内容。
- 注意：启用后提单内容会发往所配置的模型服务。测试 `test_settlement_bill_model.py` 全部使用假的模型响应；**尚未用真实提单和真实模型验证识别准确率**。

## 结汇进度图（2026-11-20）

## 单票资料组与合并办理（2026-11-20）

- `POST /api/settlement/direct-document-groups/single` 接收 `declarationNo`，首次办理才建单票组；已有单票或多票归属返回当前组，不在列表 GET/查询中批量写入。
- `POST .../merge/query` 按本单当前收货人、币种读取候选，支持关键词、出口日期及分页。申报抬头可不同；已有多票组返回禁止选入原因，匹配已有提单仅作提示，不自动选中。
- `POST .../merge/preview` 接收本单、所选报关单和可选 `sharedBillId`；后端返回完整选择的金额、条件、共用提单和按卖方＋合同号规划的合同，不按候选当前页加总。只有一份本单提单时默认共用，`0` 表示合并后再上传或核对。
- `POST .../merge` 接收同一选择、UUID `requestId` 和 `previewToken`。在 settlement 写锁内重读报关依据、归属、提单及合同，任何预览依据变化均拒绝过期提交；同一请求重复提交返回同一后继组。至少两票、包含本单、同一客户同币种、当前依据有效、都不在多票组是后端硬条件。
- 合并新建组，移动成员与资料记录，不删除旧组和文件。指定共用提单覆盖本次全部成员，其他原提单保留；旧合同保留并标记需要按新范围重新生成。合并不写入收款批次、银行流水或分配金额。
- `0053_settlement_group_merge` 为组头增加 `initial_declaration_nos`、`merged_into_id`、`merged_at`、`merged_by`。初始范围与原组头保留用于追溯，成员仍全局唯一。存在合并历史时拒绝降级丢弃关系。
- 旧组只读链接及文件可跟随后继组；旧组写操作拒绝，提示刷新新组。列表不再列出已合并旧组。`grouping=single/multiple/all` 由后端过滤；旧手动创建 HTTP 接口保留一个兼容版本，原手动建组弹窗已移除。


## 总览账龄与待办（2026-11-20）

`overview/query` 新增 `insights` 和 `asOf`，复用完整报关应收汇快照；按币种返回未结汇账龄、待处理事项和已结汇报关金额。账龄从出口日期起算，金额为尚未结汇报关单的完整报关金额；缺出口日期单独提示，仍计入未结汇合计。已在香港到账但尚未汇回的报关单仍属于未结汇。

香港超期沿用到账后超过 30 天的规则；补资料只统计资料缺失或合同失效的已收香港批次；直接催收按逐单 FIFO 未收推算。待办跳转现有批次、登记或客户总账页面，保留客户范围；报关单明细同时保留币种筛选，其他工作区按币种分别展示，不执行写操作。客户表按未收差额排序，进度宽度封顶 100%，实际百分比保留超收；客户实收仍取实际到账、手续费单列，不用逐单推算覆盖原总览口径。分页只影响客户表，账龄和待办始终覆盖全部筛选结果。


## 香港回款人工登记（2026-11-20）

- `POST /api/settlement/hk-workbench/receipt-preview`：读取全部所选报关单，返回选单信息、历史收款账户、Decimal 金额、差额、逐项核对和 `submit.allowed/reason`。
- `POST /api/settlement/hk-workbench/register`：人工登记日期、到账金额、手续费和流水信息；事务内重读有效依据与批次占用，要求同一香港收货人、同币种且到账加手续费与报关合计严格对平。手续费超过预警线只提醒。原 `/batches` 接口保留一个兼容版本的可先登记实际到账行为。
- 可选 `bankSlip {fileName, content}` 为 base64 PDF，最多 8 MiB；校验格式、可读、非加密与至少一页，不提取字段或进行 OCR。文件在事务外保存，元数据与批次同一事务绑定；提交失败清理未关联文件，幂等重试沿用原批次与原件。
- `GET /api/settlement/batches/{id}/bank-slip/file`：认证后读取原件并核验 SHA-256。`BatchDetail` 增加 `receivedSlipName/receivedSlipUrl`。
- 增量迁移 `0054_settlement_hk_slips` 只新增本模块原件关联表；存在记录时拒绝降级，不写 NS、不修改已有提单识别。

验证见 `test_hk_receipt.py`：对平与日期限制、费用预警、无效选单、服务身份只读、事务失败清理、附件完整性、幂等和 HTTP 原件下载。


销售订单口径确认（2026-11-20）：业务确认海关回执的“出口合同号”即销售订单号。页面统一称“销售订单”，生成仍沿用该回执编号；同订单同卖方合并，不同订单或不同卖方分别生成。接口和数据库兼容保留 contractNo / contract_no，不改用另查的 NS 销售订单金额，也不改变金额、签订日期和买卖方取值。


未生成销售合同的 `planned` 同步返回 `contractDate`、`portOfLoading` 和 `portOfDestination`。列表显示对应提单当前口岸与拟定签订日期（对应报关单最早出口日期减配置提前天数），不受合同抬头缺失影响；未生成日期标注“拟”，提单修改或移除后重新读取当前依据。已有合同仍展示生成文件记录的日期和口岸，变更依据后保留“需重新生成”状态，不把新计划冒充旧 PDF 内容。


香港批次编号（2026-11-20）：新批次使用 `HK + UTC 创建日期 YYYYMMDD + - + 本地主键（至少五位）`，例如 `HK20261120-00004`。日期不取到账日期，主键全库递增、不每日重置。历史 SB 编号保持原样；查询、资料链接、导出及幂等重试均沿用已保存的批次号，不自动改写历史编号。


## 资料组缺陷修复（2026-11-20）

- `GET /api/settlement/direct-document-groups/{id}/source-preview` 返回原客户/币种、当前客户/币种、完整组金额、成员数、`token` 与 `update.allowed/reason`。当前全部成员仍为有效直接收汇、同客户同币种且与原组依据不一致时，允许经办人确认。
- `POST .../{id}/source` 只接收 `{token}`，在 settlement 写锁内重新读取当前依据与组归属。过期预览、旧合并组、无效依据、组内跨客户/币种均拒绝。确认后更新组客户/币种，并在 `basis_history` 保存前后依据、回执版本、UTC 时间和认证操作者。保留提单、合同及收款事实；旧合同按现有摘要重新判定失效，不自动重生成。来源已不满足同客户同币种条件时，仍须先核对来源，不能用更新入口绕过约束。
- `GET .../merge/requests/{requestId}` 返回 `{group: DocumentGroup | null}`。空值仅表示暂未查到已提交结果，客户端仍保留原确认请求供幂等重试；后端仍在原合并写入口优先复用已完成请求。
- 提单上传在解析文字/OCR 之前检查 PDF 可读、未加密、至少一页且页面内容流可读取。有效扫描件可人工补填，损坏文件不能登记。银行水单复用校验函数，继续不做 OCR。资料组打包再次校验原件，已有损坏文件拒绝进入资料包。
- 资料组内相同 SHA-256 的提单在 ZIP 中只写一份，文件清单合并列出覆盖报关单；数据库关联记录与原件不删除。
- 列表先以 SQL 成员计数筛选单票/多票；默认先分页后读取当前页资料。关键词及进度筛选保留全量统计，当前依据、提单、合同、双方抬头和归档状态按请求批量读取，不逐组执行相同查询。快照仅在当前请求内使用，不跨请求缓存状态。

增量迁移 `0055_settlement_group_basis` 仅新增可空审计 JSON 字段；有来源更新记录时拒绝降级丢失历史。专项验证：`backend/tests/settlement/test_document_group_fixes.py`，包含隔离 MySQL 并发更新、查询次数与分页一致性。
