# 发票与子采购单匹配

比较已入库发票与本地已同步的 NS 子采购单，不需要 NS 发票。支持候选推荐、逐项差异、整票关联多张子采购单，以及需要拆票时的人工数量分配；不回写 NS，不自动批准候选。

## 文件与依赖

controller 负责身份及 DTO，service 管理评估和短事务，policy 负责名称、备注与数量金额规则，dao/entity 只访问本模块分配表。发票和采购数据通过 invoice/public.py、business/public.py 读取，同一确认用例复用同一业务库连接。应用工厂注入已有 InvoiceService、PurchaseMatchingSource 和业务库引擎。

## 接口

- `POST /api/matching/summaries`：只读批量摘要。请求 `invoiceIds` 为1—100个十进制字符串ID，拒绝不可见、停用或非进项发票；超出无符号64位范围返回422。响应 `rows` 每项含 `invoiceId/method/confidence/validation/tone`，不返回其他身份的数据或原始来源快照。当前页共用一次采购查询和关联查询。摘要复用六项比对及来源摘要检查；只有整票逐行覆盖且候选唯一、采购明细不重复、条件允许时才显示高可信。保存的人工差异保持“已确认（有差异）”，来源变化优先显示待复核；数量分配区分部分与完整。任何读取失败均显式报错，不返回假未关联状态。票面状态及导入校验不随人工确认改变。

- `GET /api/matching/invoices/{invoice_id}`：可选查询参数 `customsNo`（CD编号或18位报关号码），供调用方补充报关线索；现有前端未提供该输入。返回发票、候选、六项检查的两侧值及差额、定位依据、剩余数量、建议分配数量、allowed/reason、snapshot、已确认分配。当前最多展示100个候选并明确提示截断，不把未展示项视为未匹配。
- `POST /api/matching/invoices/{invoice_id}/confirm`：JSON 包含 requestId（UUID）、snapshot、invoiceLineId、purchaseLineId、quantity，以及可选 `customsNo`；确认时重新核对同一报关线索。ID及数量为字符串，数量最多18位整数与8位小数；拒绝多余字段。金额由后端按子采购行含税金额和报关数量累计分摊，不接受前端金额或操作者。
- `POST /api/matching/invoices/{invoice_id}/links`：整票关联。JSON 包含 requestId（UUID）、snapshot、`pairs`（每项仅 `invoiceLineId`、`purchaseLineId`）及可选 `customsNo`，拒绝数量、金额等多余字段。一次选择多条子采购明细，可以来自多张子采购单。服务端按每条发票明细汇总所选子单的报关数量与人民币含税金额，逐行精确相等且所有发票明细均覆盖后，原子保存关联关系。返回已关联明细数，不写分配台账。正式匹配页提供候选勾选和确认入口，错误及不可操作原因来自后端。
- 参数格式错误沿用全站400；来源过期、幂等键冲突返回409；业务条件不满足返回422；存储未配置、失败或提交结果不明返回503。

## 手动搜索、复核与差异确认

- GET 另支持 `purchaseQuery`（子单号、母单号、供应商或品名）、`invoiceLineId` 和 `page`，用于手动搜索。在当前身份可见的已同步子采购中匹配，不限于自动候选。后端分页，每页100条，返回 `page/hasNext/candidateCount`。查询不改变来源快照；换页、换查询可保留已选关系。
- `POST /api/matching/invoices/{invoice_id}/links/review`：接收 `snapshot/pairs/customsNo`，只读复核所选关系，返回 `allowed/reason/warnings/requiresManualConfirmation`。汇总数量、金额和差异均由后端计算，不创建记录。
- `/links` 另接受 `manualConfirmation`（严格布尔值，默认false）与 `manualReason`（最多1000字）。可人工核实的差异必须明确确认并填写非空说明；不传确认时仍执行原有严格校验。人工关联可使用搜索得到的任意可见子采购明细，不受自动候选前100条限制。
- GET 返回 `manualLinkAllowed/manualLinkReason` 供页面展示整票人工关联能力；`linkAllowed` 和数量分配的 `allowed` 保持原有严格含义。前端不自行计算或判定差异。

## 匹配规则

当发票备注没有母采购单号时，API 调用方可传入 CD 编号或18位报关号码；该线索仅用于定位候选，确认分配时会按同一号码重新核对。现有前端暂不提供该输入。

备注中的完整子采购单号或母采购单号优先召回；没有采购单号时，用备注中的报关单号（CD编号或真实报关号码）定位直接关联的子单；两者都没有时，按销售方同名主体与报关品名召回。不把 PO100 当作 PO1001。备注命中但供应商不同仍展示候选，直接列出双方名称及“匹配不一致”报警，不能标为高可信。名称仅统一全半角与空白，发票品名去掉开头税收分类前缀；简称、别名、模糊商品、单位换算未自动处理。销售方与供应商名称不同但人工核实可以关联时，使用整票人工确认并记录依据，不自动删除地名等前缀，也不修改来源名称。

逐行比较供应商、子采购报关品名、报关数量、子采购报关单位、按报关数量折算的含税单价及子采购行含税金额。报关数量与报关单位必须成对使用；不能用子采购原始单位或母单单位补空。完整数量时比较行金额；部分开票时严格比较发票金额与子单行金额的比例。含税单价展示值保留8位，仅供阅读；校验用原始行金额与数量交叉相乘，不用展示舍入值。报关单金额若为美元，不与人民币发票金额直接比较。

供应商、品名、报关数量／单位、含税单价和采购含税金额六项全部一致才标记为高可信候选；这不等于已确认分配。数量分配继续执行原有严格规则：正常状态、两侧明细完整、购方名称与采购公司一致、币种明确一致、销售方与子单供应商主体一致、来源金额成比例且剩余数量／金额足够，才允许人工确认。以两侧剩余数量较小值作为建议，支持一票多单、一单多票逐次保存；多个高可信候选明确提示人工确认，不自动选第一条。红冲、负值、来源缺失、未核实购方及币种不能绕过校验。

整票关联按同一发票行汇总所选子单的数量、金额。供应商名称、品名、单位、数量／金额汇总不一致、备注线索冲突及票面状态未知，可在人工核实后填写说明确认；差异保留为差异，不改称自动匹配一致。购方与采购公司、币种、来源明细完整性、正数数量及金额、发票抬头与明细总额一致、全部发票行覆盖仍为不可绕过条件；红冲／作废、重复关联、已有数量分配、来源变化仍拒绝。

人工确认只保存对应关系，不产生数量分配、不开票、不回写NS；所选子采购明细被整票关联占用，不能再用于另一发票或数量分配。需要一单多票或分批数量分配时仍应使用原有严格分配路径。

## 持久化与恢复

业务迁移 `0004_invoice_allocations` 新增 `invoice_purchase_allocations`；`0007_invoice_purchase_links` 新增整票关联批次和明细表。运行 `npm.cmd run db:business:upgrade` 后重启后端。启动不自动迁移，未迁移不能确认。迁移不改现有来源记录。2026-09-24 已将本机配置的业务库从 `0005` 升级至 `0007`，只读核对三张匹配表存在，迁移前后分配及整票关联记录均为 0；其他环境仍须分别迁移。

确认先锁定当前身份发票，再按采购主键顺序锁定当前身份采购记录；读取分配使用锁定读，避免MySQL可重复读旧快照造成超分配。第一期在身份范围内串行确认，可能影响同身份大量数据的确认耗时，未宣称高并发性能。外部HTTP不进入持锁事务。

snapshot绑定当前来源及占用，提交前重算，不接受过期结果。requestId在租户内唯一，同一请求重放不重复占用；相同键不同内容拒绝。提交结果不明时先刷新记录核实，再沿用原请求键重试，不能自动换键重发。

每次确认保存数量、含税金额、操作者、UTC时间及当时票面/候选快照。来源变更后显示待复核，保留已有占用，不自动释放。当前没有取消、红冲调整或审批/回写入口；这些需单独设计状态流转，不通过直接删分配处理。

整票关联另存请求幂等键、操作者、发票及所选候选的不可变快照、发票行与子采购行、确认时双方来源摘要；GET 返回 `links` 及 `needsReview`。来源变化保留已确认关系并标记待复核，不自动重选或释放。

人工确认复用批次的 `source_snapshot` 保存 `manualConfirmation/manualReason/warnings`，无需新增迁移。GET 关联历史返回这些字段；说明与差异确认选择参与请求幂等内容核验，操作者来自认证身份。页面对明确的400/422允许修正表单；结果不明时保留请求标识并要求先核实。更新前后端后需重启后端，旧接口会显示更新提示。
