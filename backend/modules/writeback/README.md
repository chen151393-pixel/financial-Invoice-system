# 回写模块

2026-10-28 实现阶段 A/B（整票审核后持久入队、只读账单查询、不可变分配方案），以及按[回写方案](../../../docs/ns-invoice-writeback-plan.md)第 1.1 节简化的阶段 C（冻结写入请求、回写预览、写入 NS、结果不明时人工核实）。不做 NS 请求账本和自动续做。旧 `archive/writeback` 分支的通用预览执行器未恢复，旧库三张 NS 审计/锁表不修改。

## 职责与文件

- `service/queue_service.py`：订阅 matching 最终用例事件，同一事务判断整票就绪、入队和失效；不调用外部系统。
- `service/task_service.py`：列表、详情、历史检查、带版本与幂等编号的方案确认；方案冻结时同时冻结发送 NS 的正文与预览。
- `service/execute_service.py`：确认预览、写入 NS（短事务加账单锁并登记执行中，事务外调用写入 RESTlet，再短事务记录结果）、结果不明或部分完成时的人工核实、后台自动写入。
- `service/query_service.py`：领取五分钟只读租约，事务外调用已部署的查询 RESTlet，保存前重新核实审核快照及租约。
- `service/prepare_worker.py`：可配置的后台历史补扫（每批 25 张）及候选查询（每轮最多 4 个任务）；等待账单十分钟后再查。查询错误为 blocked，由用户核实后重查。写入开关开启时每轮再自动写入最多 4 个待写入任务。
- `policy/plan_policy.py`：供应商、母单、子公司、币种、精确子采购归属、逐分配金额守恒和同账单本次合计校验。累计与明细不一致的账单不在此阻断。
- `policy/preview_policy.py`：按账单合并方案金额，生成发送 NS 的正文（写前累计 `expectedBefore`）和逐账单预览；写后累计＝写前＋本次。
- `policy/result_policy.py`：解释写入 RESTlet 返回；格式、账套、请求编号或账单结果无法核对时一律按结果不明。
- `policy/write_gate.py`、`policy/state_policy.py`：写入开关、写入接口配置与供应商白名单；已写入状态与执行中超时规则。
- `entity/`、`dao/`：任务、发票当前任务指针、只追加方案、审计（迁移 `0036_writeback_prepare`），写入请求与账单目标锁（迁移 `0037_writeback_execution`）。

## 依赖与规则

通过 matching 的 `public.py` 读取整票审核快照；matching 经 invoice、review、source 的公开门面读取依据与身份。事件订阅仅在 `app.py` 装配，外部查询服务由入口注入。

整票须正常、正金额、税额已知且不为负（零税额照常登记）、人民币、明细完整，各行金额及数量完整确认，无待审建议，有效发票和采购依据版本一致。单位换算证据与结果必须匹配。来源须有效、同账套/供应商/采购公司，销售方名称规范化核对通过，NS 供应商、母单、币种内部 ID 完整。购买方为空时不单独阻止入队；有值且与采购公司规范化名称不一致时，返回“票面购买方与采购公司身份待核实”（2026-10-29 确认）。不补造缺失购买方，不放宽母采购供应商关系、采购公司或目标账单归属校验。不满足条件时，整票状态查询接口返回具体未就绪原因，不创建可确认任务。

任务与审核快照按 `(invoice_id, fingerprint)` 去重。确认、人工分配、批量确认、原子替换的最后一步发出整票事件；取消、发票换版、采购依据变化使旧任务失效。写库失败会回滚整笔审核。使用现有数据库账本锁和唯一约束串行化本地变更。

唯一候选不等于归属明确：仅非历史任务、精确子采购关联唯一、真实 `subsidiary:*` 公司映射且全部校验通过时自动冻结方案。`classification:*`、空子采购关联、多候选、历史扫描均需人工确认实际子公司与账单归属，并保存证据。明确关联其他子采购的账单不能人工覆盖。查询结果不预留额度；即使 ready，也不能写入 NS。

确认需当前 `revision`、UUID `requestId`、`confirmScope: true`、5–1000 字依据和完整 `orders: [{subPurchaseOrderId, billId}]`；前端不提交金额，由后端审核快照汇总。兼容的 `allocations` 请求也须满足整单不拆分、逐明细金额不变且覆盖完整的约束。相同请求与身份重复提交返回原处理后的当前状态，正文或身份不同返回 409。重新查询清除当前方案指针并增加版本；旧方案与审计仍保留。

## 写入规则

- 方案冻结时生成写入请求：正文（发票号码、开票日期、含税金额、每张账单的母单、本次金额与写前累计）和预览只写一次，不再修改。一张发票最多 20 张账单，超过时任务为“待处理”。
- 有账单累计与明细不一致时任务为“待确认回写预览”，人工确认后才进入“待写入 NS”；全部一致时直接进入“待写入 NS”。
- 写入前检查写入开关、写入脚本配置和供应商白名单（`WRITEBACK_VENDOR_ALLOWLIST`，空为全部不允许，`*` 为全部允许），并对全部账单取持久锁；账单被其他请求占用时返回 409。
- NS 调用在事务外。请求未发出（连接失败、401/403、开关关闭）回到“待写入 NS”并释放锁；发出后超时、非 2xx、非 JSON 或返回无法核对，一律为“结果不明”，保留锁。
- `APPLIED` 为“NS 已登记”；`CONFLICT`（同号发票已登记）为“NS 已有同号登记”；`REJECTED` 及确认未写入的错误为“待处理”，均释放锁。`PARTIAL` 为“部分写入，待核实”，保留锁。
- “结果不明”“部分写入”以及执行中超过 10 分钟的任务只能人工核实：标记“NS 已完整登记”，或（仅结果不明）“NS 没有任何写入”后回到待写入。没有直接重发入口。
- 已发出或已写入的任务（执行中、部分写入、结果不明、已登记）不因审核变化转为失效，也不能重新查询；审核变化只记入原因，提示人工核对 NS。启动时不清除执行中状态或账单锁。

## 接口

列表搜索拆为 `taskNo`（任务号）、`invoiceNo`（发票号码）、`supplierName`（供应商）和 `parentOrderNo`（母采购单号），非空条件按 AND 组合、去除首尾空白并做转义包含匹配；旧 `keyword` 混合搜索仍兼容。母单号仅查任务不可变审核快照 `snapshot.sources.*.parent_number`，不查候选账单、备注或实时来源。列表、分页总数和状态概况共用同一搜索表达式；一个任务匹配多个母单也只计一次。任务摘要新增去重的 `parentOrders: [{id, number}]`，列表展示该任务的全部母单，历史快照缺失时为空。不增加表或修改历史快照。

列表概况分为待回写（`queued/waiting_bill/needs_confirmation/needs_preview/ready`）、回写中（`executing`）、NS 已登记（`applied/conflict`）、需处理（`blocked/partial/unknown`），审核已失效（`stale`）单独筛选。2026-10-30 起，新旧同号已有登记任务均计入“NS 已登记”，不再进入“需处理”，无需重查或数据迁移。分组只用于查询展示，保留 `conflict` 及其“NS 已有同号登记”细分说明，不改变允许动作或将已有登记改记为本次写入成功；部分写入与结果不明仍须人工核实。

列表新增 `group=pending|executing|applied|attention|stale`（空为全部），与原 `state` 精确筛选共同生效。响应新增 `counts`（`all` 与五个分组）及 `states`（12 个细分状态的 `state/label/group/count`）。全部计数由数据库按组合搜索条件汇总，沿用任务号／发票号／供应商的相同转义包含查询，不受状态、分组和分页限制，也不调用外部 NS。搜索条件无匹配记录时返回零计数。无表结构或迁移变化。

全部需要现有认证身份；服务身份不能人工确认、重新入队、确认预览、写入或核实结果。

2026-10-29：本地回写取消来源账套隔离。列表、详情、发票关联任务及后台处理均不按任务来源账套过滤；查询和执行使用服务器当前配置的 NS 连接。来源账套仅保留作历史追溯，不生成额外提示、不禁用按钮，也不与查询返回账套比较。查询适配器仍验证结果来自当前连接；供应商、母采购、子公司、币种、金额和账单状态继续校验。账单执行锁按实际连接账套建立；写入开关、白名单、幂等请求及结果未知时禁止重发的规则不变。

## 整张子采购单分配（2026-10-29）

回写分配以审核快照内的整张子采购单为最小单位，每张子采购单只能选择一张账单。金额为该发票对该子采购单的全部已审核分配之和，不取整张母采购金额。按 NS 子采购内部 ID 归组，商品明细仅作核对与追溯，不能新增、移除或修改单独明细的回写金额。

详情新增 `orders`（子采购 ID、单号、母单、金额、明细及后端筛选的 `eligibleBillIds`）；冻结方案新增只读 `orders` 展示投影，原始 `allocations` 仍保留。选择不同母单、其他子采购明确关联的账单、漏选、重复选择及超出同账单合计额度均由后端拒绝。多个子采购单可选同一账单，预览与 NS 正文按账单合并一次，含税合计须等于发票金额。

历史方案正文和审计不改写。历史拆单方案保留实际分配展示，执行前重新检查整单约束，不符合时须重新查询账单并确认方案。本次验证只使用隔离测试及本地只读快照，不调用 NS 写入。

## 查询阶段核对已有登记（2026-10-30）

`query_service` 使用审核快照的供应商内部 ID 和本张发票完整号码，通过 source 查询门面读取 NS 同号有效登记。结果保存在 `candidates.registrationCheck`，包含核对号码和已有记录的 ID、号码、日期。查到记录优先进入 `conflict`（“NS 已有同号登记”），归入“NS 已登记”，不生成方案，不允许确认或执行；不将其当作本次回写成功。额度为零不能单独证明本张发票已登记。

`policy/registration_policy.py` 供方案确认、执行和动作展示复用。历史待写入任务若没有本张发票的核对结果，必须重新查询；查询失败、旧脚本未返回核对结果时阻塞，不按未登记放行。写入 RESTlet 仍保留最终同号检查，防止查询后已有新登记。无需数据库迁移，NS 只读查询脚本须先升级到 `2026-10-30.4`，详见部署说明。
