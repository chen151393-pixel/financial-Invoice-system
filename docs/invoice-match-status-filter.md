# 进项发票按匹配状态筛选：设计方案

状态：**方案 A 已实施**（2026-10-27）。第 9 节待确认项按建议处理：红字、已被红冲、作废归为不参与比对；部分匹配单独一档；页面统一新文字；升级到方案 C 的阈值为单次范围 20,000 张或 p95 1.5 秒。

## 1. 目标

进项发票列表（`/invoices`）增加“匹配状态”筛选：全部 / 已匹配 / 部分匹配 / 待审核 / 待复核 / 未匹配 / 不参与比对，并显示各状态张数。筛选结果与其他条件（关键字、柠檬云账套、票面状态、开票日期）取交集，分页和总数按筛选后的结果计算，不能只筛当前页。

## 2. 现状与约束

| 事项     | 现状                                                                                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 列表     | invoice 模块 `GET /api/invoices`：只读本模块票头，SQL 分页，按开票日期倒序、主键倒序                                                                                       |
| 匹配状态 | matching 模块 `POST /api/matching/summaries`：页面拿到当前页发票 ID 后再查，规则写在 `MatchingQueryService.summaries` 中                                                   |
| 状态规则 | 有已通过但复核失效的分配 → 待复核占用；有效通过的发票行数 ≥ 发票有效行数 → 已比对；部分行有效通过 → 部分比对；只有待审核建议 → 待审核建议；其余 → 未比对                   |
| 已有先例 | `GET /api/matching/invoice-totals`：matching 通过 invoice 门面 `read_invoice_amount_scope` 按列表筛选条件分批（每批 500 张）读取票头，在 matching 内汇总待匹配、待复核金额 |

约束（`AGENTS.md`、后端规则）：

- 依赖方向已经是 matching → invoice（matching 读 invoice 门面）。invoice 不能反过来导入 matching，否则形成循环依赖。
- DAO 只访问本模块的表，不能在一条 SQL 里把 `invoice_headers` 与 `matching_allocations` 连接起来。
- 修改其他模块的数据只能通过事件，由订阅方在同一事务中处理。
- 前端不推断业务状态：张数、状态都由后端给出。

因此“按匹配状态筛选”只能由 matching 组织：matching 算出状态，再按发票 ID 范围让 invoice 门面分页。

## 3. 状态定义（统一成一个策略函数）

matching `policy/invoice_match_policy.py` 的纯函数 `match_status`，列表筛选、计数和 `POST /api/matching/summaries` 共用，同一张发票在任何地方显示的状态都一样。

| 状态键         | 页面文字   | 判定（按顺序）                                                                                                                                                       |
| -------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `needs_review` | 待复核     | 存在已通过但复核失效（`verification_status != valid`）的分配。**实施调整**：排在“不参与比对”之前，红字或作废发票上仍有待复核的占用时提示待复核，避免待处理工作被隐藏 |
| `excluded`     | 不参与比对 | 票面展示状态不是正常：红字（负金额）、已被红冲、作废、未知（invoice 门面 `invoice_display_status`）                                                                  |
| `confirmed`    | 已匹配     | 有效通过的发票行数 ≥ 发票有效行数（且有效行数 > 0）                                                                                                                  |
| `partial`      | 部分匹配   | 部分发票行有效通过                                                                                                                                                   |
| `proposed`     | 待审核     | 没有有效通过的行，但有待审核建议                                                                                                                                     |
| `none`         | 未匹配     | 以上都不满足                                                                                                                                                         |

## 4. 方案对比

### 方案 A：matching 实时计算后按 ID 分页（推荐先做）

1. matching 新增查询接口，接收与列表相同的筛选条件 + `matchStatus` + 分页。
2. 在同一只读快照（MySQL `REPEATABLE READ`，同 `invoice-totals`）中，通过 invoice 门面按筛选条件分批读取范围内全部发票的 ID、票面状态、有效行数；每批再读本模块的分配，套用第 3 节策略，得到每张发票的状态。
3. 同一次扫描顺带算出各状态张数（给页面的分段按钮用）。
4. 选中状态的发票 ID 集合交给 invoice 门面，由 invoice 按原有排序做 SQL 分页，返回与 `GET /api/invoices` 完全相同的行结构。

| 优点                                                                                  | 缺点                                                 |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 不加表、不迁移；规则只有一处，不会和比对页不一致；改动集中在 matching 和 invoice 门面 | 每次查询都要扫描筛选范围内的全部发票；范围很大时变慢 |

估算：每批 500 张两次查询，5,000 张约 20 次查询，预计 1 秒内。

### 方案 B：在 invoice 票头加“匹配状态”冗余列，由事件维护

matching 每次分配变化时发布事件，invoice 订阅后在同一事务中更新 `invoice_headers.match_status`，列表直接按本表字段筛选和分页。

| 优点                              | 缺点                                                                                                                                                                                                                   |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 查询最快，列表仍完全在 invoice 内 | 状态规则依赖 matching 的分配与 invoice 的行数，冗余列由 invoice 保存、却靠 matching 判定，职责交叉；分配建议、通过、驳回、取消、复核、重建、发票换版等每条写路径都要发事件，漏发一处状态就失真；需要迁移和历史数据回填 |

### 方案 C：matching 自己的状态投影表（量大后升级）

matching 新增 `matching_invoice_states(invoice_id PK, status, best_confidence, proposed_count, confirmed_count, updated_at)`。在 matching 自己的分配写事务中，以及已订阅的 `InvoiceChanging` / `InvoiceChanged`（发票换版）处理中，同步重算受影响发票的状态；按状态取 ID 集合时只读本表，再交给 invoice 门面分页。“未匹配”取范围内不在投影里、或投影为 `none` 的发票。

| 优点                                                     | 缺点                                                                                                        |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 状态归 matching 所有，符合模块边界；查询不用扫描全部发票 | 要迁移、回填；分配的每条写路径都要重算投影（与方案 B 同样要求写路径齐全，但都在本模块内，可用测试逐条覆盖） |

### 结论

**先做方案 A**：规则唯一、改动小、数据量在可接受范围。出现以下任一情况时升级到**方案 C**，接口和页面不变，只替换 matching 内部的取 ID 方式：

- 单次筛选范围的发票超过 20,000 张；或
- 该接口 p95 耗时超过 1.5 秒。

不采用方案 B（职责交叉、写路径分散在两个模块）。

## 5. 接口设计（方案 A）

### matching：`POST /api/matching/invoices/query`

请求（与列表筛选同名，增加匹配状态）：

```json
{
  "q": "",
  "account": "",
  "status": "",
  "date_from": null,
  "date_to": null,
  "matchStatus": "all",
  "page": 1,
  "page_size": 20
}
```

- `matchStatus`：`all | confirmed | partial | proposed | needs_review | none | excluded`。
- 其余字段的校验沿用 invoice 的 `InvoiceQuery`（日期先后、长度、页大小上限 100）。

参数校验失败按项目约定返回 400。

响应：

```json
{
  "list": {
    "total": 37,
    "page": 1,
    "pageSize": 20,
    "hasPrevious": false,
    "hasNext": true,
    "rows": [],
    "amounts": []
  },
  "counts": {
    "all": 424,
    "confirmed": 300,
    "partial": 12,
    "proposed": 37,
    "needs_review": 4,
    "none": 65,
    "excluded": 6
  },
  "summaries": [
    {
      "invoiceId": "1",
      "status": "proposed",
      "label": "待审核",
      "tier": "high",
      "proposed": 2,
      "confirmed": 0
    }
  ]
}
```

- `list` 与 `GET /api/invoices` 的 `InvoiceList` 结构相同，`amounts` 为筛选后范围的票面汇总。
- `counts` 不受 `matchStatus` 影响，只受其余筛选条件影响。
- 顺带返回本页的 `summaries`，页面不用再单独请求 `/api/matching/summaries`。

### invoice 门面新增（只读，不含 matching 概念）

| 函数                                                                           | 作用                                                                                              |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `read_invoice_status_scope(connection, filters, *, after_id=0)`                | 按列表筛选条件分批返回 `[{id, status, amount_including_tax, active_item_count}]`，每批至多 500 张 |
| `read_invoice_page(connection, filters, *, include_ids=None, page, page_size)` | 与列表相同的排序和分页；`include_ids` 不为空时只在这些 ID 内分页，返回 `(total, amounts, rows)`   |

`GET /api/invoices` 保留不变，供其他调用方使用；列表 SQL 抽成一处，两个入口共用。

## 6. 前端交互

- 进项发票的列表卡片中，查询栏下方加“匹配状态”分段按钮，每个选项带后端给的张数：全部 / 已匹配 / 部分匹配 / 待审核 / 待复核 / 未匹配 / 不参与比对。
- 列表改为请求 `POST /api/matching/invoices/query`，切换状态时回到第 1 页；匹配状态写入地址（`?match=proposed`），刷新或分享链接后保持。
- 表格中“比对状态”列直接用响应里的 `summaries`。
- 概况卡与分布图仍按票面筛选条件统计，不随匹配状态变化（在卡片说明中注明）。
- 加载、空结果（“当前条件下没有待审核的发票”）、失败、重试照常处理；状态文字与颜色同时出现，不只靠颜色区分。

## 7. 一致性与边界

- 统计与分页在同一只读快照内完成，防止扫描期间有分配通过或发票换版，造成张数与列表不一致。
- 扫描上限：单次范围超过 20,000 张时返回提示“范围较大，请缩小账套或日期”，同时仍返回已计算的结果；这也是升级到方案 C 的信号。
- 只读接口，不触发比对、重建或任何写入。

## 8. 测试计划

- **策略**：六种状态逐一判定；红字、作废归为“不参与比对”；行数为 0 的发票不算已匹配。
- **服务**（SQLite）：筛选与匹配状态取交集；分页总数按筛选后计算；`counts` 不随 `matchStatus` 变化；`summaries` 与旧接口结果一致；跨批（> 500 张）扫描正确。
- **HTTP**：未登录 401、参数校验 422、`matchStatus` 非法值 422。
- **MySQL**：快照隔离与大范围耗时（5,000 / 20,000 张）各测一次。
- **前端**：分段按钮张数、地址同步、空结果文案、切换回第 1 页。

## 9. 待确认

1. 红字、已被红冲、作废的发票归为“不参与比对”，不出现在其他匹配状态里。现有 `summaries` 不区分票面状态，会显示为“未比对”。
2. “部分匹配”单独作为一档，还是并入“待审核”。建议单独一档，因为它已有部分行通过。
3. 页面文字统一为“已匹配 / 部分匹配 / 待审核 / 待复核 / 未匹配”，替换现在列表中的“已比对 / 部分比对 / 待审核建议 / 待复核占用 / 未比对”。
4. 升级到方案 C 的阈值（20,000 张 / 1.5 秒）是否合适。
