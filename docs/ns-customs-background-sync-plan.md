# NS 报关单后台同步设计

状态：**设计方案，部分实施**。日期：2026-10-28。2026-10-29 已实施第 4 节定时计划的首期（计划表 `sync_ns_plans`、`sync_runs.ns_plan_id`、分页记录 `sync_ns_runs.run_id`、计划页面与批次详情，见[同步模块](../backend/modules/sync/README.md#ns-定时同步计划2026-10-29)）；手动整段后台补拉、按 CD 补拉、逐单尝试表 `sync_ns_items`、失败重拉与核实入口仍未实施。面向负责数据同步和失败处理的财务、管理员，沿用柠檬云的“手动补拉／定时计划”操作方式。

## 1. 目标与现状

目标：提交一次即可在后台拉完指定范围的报关单，自动补齐关联子采购并保存；定时回扫；每张保存失败的报关单可以按 CD 编号查到历史原因并有针对性地重拉。

现有能力可复用：

- `sync` 的 `NsRunService`、`sync_ns_runs` 已保存单页请求和结果 JSON，含逐单结果；同请求编号不重复执行。
- 前端 `useRangePull.ts` 仍推进范围翻页。关闭页面后当前已提交页可继续，但不能依赖它推进整个范围。
- `source` 的 `PlReader`、`PartialSyncService`、`StorageService` 已处理关联补齐、整页读取优化、逐关联组提交、失败隔离和内容更新。
- 柠檬云已有数据库队列、每日多时点计划、批次历史和明确失败重试，见[现有实现](lemon-background-sync.md)。

本次范围为报关单同步；关联子采购自动随报关单保存。保留子采购独立同步和其他 NS 预览入口。同步不自动审核、不创建独立开票任务、不写回 NS。

## 2. 页面结构

沿用 `/sync/ns` 入口，在报关单区域提供下列工作区；批次详情新增 `/sync/ns/batches/:requestId`，集中登记在 `app/paths.ts` 与路由表。历史列表和失败记录的视图、筛选可放 URL 查询参数，刷新后恢复。

```text
NS 报关单同步                         数据来源：当前 NS 账套
自动补齐关联子采购，后台保存并记录逐单结果

[手动补拉] [定时计划]
┌ 当前标签的表单 ──────────────────────────────────────┐
│ 手动：按创建日期 / 按 CD 编号                         │
│ 条件输入                              [提交后台同步] │
└─────────────────────────────────────────────────────┘

同步记录                              [批次历史] [失败记录]
条件栏：执行时间 / 状态 / CD 编号             [查询] [刷新]
批次或逐单结果表、分页、详情入口
```

表单和历史放在同一工作区，提交成功后直接打开对应批次详情；不要求停留页面。同步中心 `/sync` 的来源入口、计划状态和健康统计接入新的 NS 批次，避免父批次与旧单页记录重复计数。

视觉沿用 [design.md](../design.md) 和[前端规范](frontend-conventions.md)。使用公共 `AppFrame`、`Card`、`SectionHeader`、`Tabs`、`Segmented`、`FilterBar`、`DataTable`、`Badge`、`Alert`、`Progress`、`Pagination`；不复制柠檬云整页 CSS。日期输入和时间编辑按实际共用需求提取，NS 不复用柠檬云账套授权或发票业务类型逻辑。

## 3. 手动补拉

| 模式 | 输入 | 执行规则 |
| --- | --- | --- |
| 按创建日期 | 开始、结束日期，必填 | 沿用现有 NS 报关记录创建日期筛选，包含起止当天；后台继续所有页和 ID 区间 |
| 按 CD 编号 | 一个或多个完整 CD 编号，换行或逗号分隔 | 后端去重、精确定位；建议首期上限 100 个；不受创建日期窗口限制 |

- 显示当前 NS 账套，只使用服务端配置的身份，不接受浏览器提交凭证或记录类型。
- CD 编号不存在时留下“未找到报关单”记录；出现多个匹配时明确失败，不猜测。
- 提交返回 202 和持久请求编号，含义为“已加入后台队列”；页面关闭后继续全部范围。
- 每张报关单重新读取完整关联子采购，不因子采购创建日期在范围外而漏拉。
- “停止后续处理”在当前关联组提交结束后生效；已提交数据保留，未处理对象及剩余范围明确记录。停止不是失败；继续操作产生关联的新批次。
- 批次详情展示实际阶段、累计处理数、成功、失败、跳过、待核实及未处理数；总量未确定时只显示已处理数，不伪造百分比。

## 4. 定时计划

| 配置 | 建议首期规则 |
| --- | --- |
| 计划状态 | 默认关闭；保存配置后才生效；显示已保存状态与下次执行时间 |
| 每日执行时间 | 1—8 个不重复的 `HH:mm`；预填 02:00；北京时间 |
| 扫描范围 | 最近 1—366 天，包含执行当天；预填 90 天 |
| 日期口径 | 报关单在 NS 的创建日期，沿用当前查询规则 |
| 执行范围 | 当前配置的 NS 账套中的报关单，自动补齐关联子采购 |

上述默认值是设计建议，不表示已启用计划。时点采用 Asia/Shanghai，任务时间存储 UTC；日期筛选仍按 NS 当前查询时区解释，界面明确标注二者口径，不暗中调整 NS 时区。

- 每次触发冻结实际日期范围、计划版本和 NS 连接身份范围；修改计划不改变已提交任务。
- 同一计划时点只能生成一个批次；已有活动计划批次时不叠加，完成后最多补一次合并后的最新窗口回扫。
- 服务停机错过多个时点，恢复后合并一次当前窗口回扫，不逐个补发旧时点。服务需保持运行。
- 暂停计划不取消已经提交的任务；保存计划使用版本校验，冲突返回 409。
- 同一账套的报关、子采购保存复用现有账户锁；新任务排队，不启动并发保存。调度领取需数据库锁，不能仅靠线程内标记。
- 这是创建日期回扫，**不是修改时间增量同步**。90 天前创建的单据后续发生变化，需按 CD 或历史日期手动补拉。

## 5. 失败记录与日志

“失败记录”默认显示当前仍未解决的明确失败，另有“待核实”和“全部历史”。按 NS 账套、CD 编号、执行时间、失败阶段筛选，后端分页。历史日志保留，不因重试成功而删除。

表格优先显示：CD 编号、执行时间、触发来源、失败阶段、中文原因、处理状态、操作。内部 ID、字段名和请求编号在展开详情中展示，避免重复显示多行长技术错误。

每次单据尝试至少持久化：批次与单页 ID、NS 账套及连接身份范围、CD 编号、报关内部 ID（未定位时允许为空）、明细 ID（已知时）、开始/结束时间、触发人与触发方式、执行阶段、结果、错误码、中文原因、建议处理、原失败记录与重试批次关联。供应商或子采购导致失败时，附实际相关单据身份，不保存整份敏感响应。

| 状态 | 展示与处理 |
| --- | --- |
| 已保存 | 报关及关联子采购已提交；警告单独展示 |
| 失败，未保存 | 本次关联组确定未提交；可按后端判断重新拉取；以前已保存的版本保留 |
| 未出库，已跳过 | 缺真实报关单号或没有关联子采购；不计入失败，保留原因 |
| 保存结果待核实 | 提交结果不明；不能直接重试，也不能被下一次计划绕过 |
| 未处理 | 停止或上游范围读取中断；不得显示为失败单已执行 |

可记录阶段：定位单据、读取报关、读取明细、补齐子采购、读取关联依据、校验数据、保存数据库。若列表读取就失败、尚不知道 CD，记录批次/页级错误及范围，不捏造逐单失败。

失败展示示例（来自当前报错情形，不代表已修复）：

> CD000727 · 校验数据失败 · 本次未保存
>
> 报关明细未返回申报单价，当前保存规则不允许缺失。
>
> 详情：明细 2029；字段 custrecord_swc_grossamountzj。
>
> 建议：核实 NS 字段值及读取结果，处理后重新拉取。

日志不含令牌、私钥、连接串、原始堆栈；技术堆栈留在受控服务器日志，通过请求编号关联。首期不提供删除历史功能；后续归档另定保留策略。

## 6. 重拉与恢复

- 支持“重拉本单”“重拉选中的失败单”“重拉本批次全部可重试失败单”；后者由后端查询完整失败集合，不能只取当前页。
- 新建批次，只重新读取目标报关单和它当前的完整关联组；原失败尝试不可变。任意后续批次成功保存同一报关单后，失败工作列表显示“后续已成功”，历史失败仍可追溯。
- 数据缺失/映射错误不会在同一批次自动反复重试；修正后手动重拉，或下次计划窗口内正常重读。首期不增加请求级自动重试。
- `unknown` 按账套及报关内部 ID 持久阻断所有入口的再次保存。尚未发现单据范围的未知页需阻断对应运行范围，不能凭超时释放。
- 实施时补齐只读核实入口：核对原执行器是否结束与数据库同事务提交凭据。确认已提交则恢复成功；有可靠证据确认未提交才允许新尝试。证据不足继续待核实，不能由管理员按钮直接猜测结果。
- 重启后：未领取任务继续；运行中任务先核实提交凭据，不能一律改成失败重发。停止标记、领取标记和最后完成游标持久化。

## 7. 后台执行与模块边界

```mermaid
flowchart LR
    A[手动补拉 / 定时触发] --> B[sync 创建持久批次]
    B --> C[后台分页与逐单尝试记录]
    C --> D[source 读取报关及完整关联子采购]
    D --> E[source 校验并按关联组保存]
    E --> F[同事务保存成功凭据与来源变化事件]
    D --> G[确定失败后持久化失败记录]
    E --> G
    F --> H[更新进度并推进下一页]
    G --> H
```

结果不明时停止当前批次推进，不走图中的普通失败继续路径。

- `sync` 负责 Controller、DTO、计划、批次、游标、逐单尝试日志、执行器和查询；不直接访问 `source_*` 表。
- `source` 继续负责来源读取、关联、字段和金额校验、保存与 `SourceChanged`；不复制一套同步业务规则。
- 现有 source 执行服务仍由 `app.py` 装配注入；不新增跨模块私有导入。后续实施需把新增同步完成事实设计成 source 公开事件契约，sync 订阅方使用同一 Connection 写提交凭据，订阅仅在 `app.py` 登记。
- 每组读取前先创建执行尝试。成功记录与来源保存必须同事务，避免“来源已保存、日志仍失败”的窗口；确定失败记录在回滚后独立短事务保存。记录写入失败则停止推进、保留未决尝试，不宣称整批完成。
- NS 调用位于数据库写事务外；每张报关及关联子采购一起提交，一张确定失败不回滚其他已成功组。
- 所有入口共用账户锁和单据未决检查；队列领取使用数据库互斥。保留当前应用单 API worker 的会话约束，不将调度互斥描述为全面支持多进程部署。

## 8. 存储与接口草案

优先扩展现有表，不建立另一套 NS 保存结果体系：

| 表 | 拟议用途 |
| --- | --- |
| `sync_runs` | 复用顶层批次，`source=ns_customs`，保存范围、操作者、状态及汇总 |
| `sync_ns_runs` | 扩展为父批次下的页执行记录，保留原请求与结果；增加父批次、领取状态及恢复信息 |
| `sync_ns_plans`（新增） | NS 账套计划、版本、时间点、回扫天数、下一次执行时间 |
| `sync_ns_items`（新增） | 逐单执行尝试、提交凭据、结构化失败及重试关联 |

注意：现有 `sync_runs.plan_id` 外键指向 `sync_lemon_plans`，不能直接填 NS 计划 ID。建议新增 `ns_plan_id` 指向新计划，NS 使用它并保持原 `plan_id` 为空，增加与来源一致的约束，保留柠檬云含义。NS 批次归属与权限显式保存；原 `scope_key` 是身份摘要，不能用于推导账套或扩大可见范围。

约束建议：计划范围唯一、计划版本与触发时点唯一、范围内请求编号唯一、父批次内单据尝试唯一；单页游标与每个已发现单据均持久化。日志按账套/CD/时间及批次/状态建立索引。停止、跳过、未知等状态需与现有 `sync_runs` 检查约束一起升级。

接口拟采用 `/api/sync/ns/customs` 前缀，所有业务校验、权限和 allowed/reason 来自后端：

| 方法与路径 | 用途 |
| --- | --- |
| GET `/configuration` | 连接可用性、已保存计划、下次时间、提交权限 |
| PUT `/plan` | 保存 `revision/enabled/times/lookbackDays` |
| POST `/batches` | UUID 请求编号，加 `mode=date_range` 的日期或 `mode=record_numbers` 的 CD 列表；202 返回任务 |
| GET `/batches`、GET `/batches/{requestId}` | 后端分页批次历史与逐单详情，返回实际统计及 poll 提示 |
| GET `/items`、GET `/items/{id}` | 单据日志查询、历史尝试与当前恢复状态 |
| POST `/batches/{requestId}/retry` | 新请求编号，加选定失败记录 ID 或明确全部失败范围；返回新任务 |
| POST `/batches/{requestId}/stop` | 请求停止后续处理，幂等 |
| POST `/items/{id}/verify` | 只核实执行与提交事实，返回恢复结果；不重新执行保存 |

相同请求编号与相同条件返回原任务；条件变化返回 409。定时任务身份由服务器创建，权限沿用 sync 管理能力并在执行时重新验证连接范围。普通用户不可跨权限查看其他身份的历史；获授权管理员可查当前组织账套记录。

旧 `/api/ns/sync/...` 等接口在兼容期保留，已有子采购和旧页面继续使用；报关新页面切换后不再由浏览器推进保存翻页。旧持久记录保持可查询，不删除；历史 JSON 若回填逐单索引，只提取可确认事实，不把历史 running 判成失败。兼容退出须确认全部调用方迁移。

## 9. 申报单价空值的处理边界

本方案不把“保存失败留日志”变成吞掉数据错误。`custrecord_swc_grossamountzj` 仍是唯一申报单价字段，不能改用 `custrecord_swc_unitprice` 或补 0。

2026-10-28 当前连接只读样本显示：CD000727、CD000728 的该字段查询为 NULL，CD000839、CD000840 有值。当前代码在配置字段缺失时拒绝保存。

建议将“已确认返回空值的申报单价”单独修复为可空并记录数据警告，继续由 review 禁止无法计算申报幅度的单据进入可自动审核；这属于另一个明确的字段规则修复，实施时需针对性测试。不能把权限失败、字段拼错、接口异常统统降级为空值。该建议尚未实施，日志功能应在现有严格规则下也能正常记录失败。

## 10. 实施顺序与验收

1. 补齐同步日志和同事务成功凭据、单据结果核实；新增迁移并更新数据库设计，不修改已执行迁移。
2. 将整个日期范围交给持久后台执行，增加按 CD 补拉、批次详情和失败重拉。
3. 接入每日计划、重复触发保护、重启恢复、暂停及停止，整合同步中心统计。
4. 用统一组件库实现表单、日志查询和详情；更新 source/sync 模块文档及接口中文说明。

必须覆盖：

- 关闭浏览器后范围任务继续；刷新按原请求恢复；同请求不重复执行。
- 多页与大 ID 范围、空结果、重复 CD、未找到 CD、子采购跨日期范围补齐；重拉更新原单不新增重复来源。
- 同批一单失败、其他单成功；跳过与警告独立计数；范围读取失败不伪造逐单结果。
- 日志失败、保存提交结果不明、服务重启、计划与手动竞争、重复时点、错过时点、计划版本冲突。
- MySQL 验证领取竞争、同事务凭据、账户互斥及未知单据阻断；SQLite 不代替这些结论。
- 桌面和窄屏的表单、日志长原因、表格溢出、加载/空/失败/正常状态、键盘焦点；演示数据明确标记。
- 实施时执行前端 build/lint/typecheck/test:web、后端 test:api/lint:api、架构检查；上线前目标环境迁移和小范围真实只读同步验收，计划保持关闭直到配置完成。

本次交付仅为方案文档；未修改业务代码、创建数据库表、启用计划或执行新的同步。
