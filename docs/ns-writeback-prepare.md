# NS 回写：部署与验证

2026-10-28：阶段 A/B 已实现；阶段 C 按[回写方案](ns-invoice-writeback-plan.md)第 1.1 节的简化口径完成代码，**尚未在 NS 部署写入脚本，也未做真实写入验收**。

当前流程：**整票审核 → 生成回写任务 → 查询候选账单 → 确认并冻结方案 →（账单累计与明细不一致时）确认回写预览 → 写入 NS**。

## 1. 部署

### 1.1 本系统

1. 停止旧后端，保留 `.env` 与既有本地配置。运行 `npm.cmd run db:business:upgrade`，确认业务库迁移达到 `0037_writeback_execution`。
   - `0036_writeback_prepare` 新增四张 `writeback_*` 准备表；`0037_writeback_execution` 新增写入请求表 `writeback_requests` 和账单目标锁表 `writeback_target_locks`。
   - 两个迁移都只建新表，不删除旧表，不能降级。
2. 配置以下开关与 RESTlet 编号，重启后端；前端发布使用 `npm.cmd run build`。

```dotenv
WRITEBACK_QUEUE_ENABLED=true
WRITEBACK_QUERY_ENABLED=true
NETSUITE_VENDOR_BILL_QUERY_SCRIPT=486
NETSUITE_VENDOR_BILL_QUERY_DEPLOY=1
# 写入脚本部署后填写；未填写时不会写入
NETSUITE_VENDOR_BILL_WRITEBACK_SCRIPT=
NETSUITE_VENDOR_BILL_WRITEBACK_DEPLOY=
# 首次写入前保持 false
NETSUITE_WRITE_ENABLED=false
# 允许写入的 NS 供应商内部 ID，逗号分隔；留空为全部不允许，* 为全部允许
WRITEBACK_VENDOR_ALLOWLIST=
```

| 开关 | 作用 |
| --- | --- |
| `WRITEBACK_QUEUE_ENABLED` | 默认 true。控制审核后入队及补扫；关闭后旧任务仍会因审核变化而失效 |
| `WRITEBACK_QUERY_ENABLED` | 默认 false。控制后台补扫和只读自动查询；关闭时可在任务详情手工查询 |
| `NETSUITE_WRITE_ENABLED` | 写入总开关。关闭时任务停在“待写入 NS”，页面没有写入按钮，后台不写入 |
| `WRITEBACK_VENDOR_ALLOWLIST` | 供应商白名单。不在名单内的任务同样停在“待写入 NS” |

写入总开关开启且写入脚本已配置时，后台每 10 秒自动写入最多 4 个“待写入 NS”且供应商在白名单内的任务；任务详情页也可点“回写到 NS”立即写入。

## 2. 写入脚本做什么

一次请求只登记一张发票，账单最多 20 张。处理顺序：

1. **同号检查**：按“发票号码＋供应商”查已有发票记录，查到即返回 `CONFLICT`，不写入。这只是提示性检查，不保证并发下不重复（方案第 1.1 节）。
2. **复核账单**：逐张检查供应商、母采购、已批准、未作废、累计已收等于本系统冻结的写前值、本次金额不超过可收额度。任一不符返回 `REJECTED`，不写入。
3. **建发票记录**：一次保存主记录（名称为发票号码、开票日期、供应商）和每张账单一行明细（账单、母采购、应收、此前已收、本次收）。子采购字段留空。
4. **更新账单**：逐张把“供应商发票金额”设为写前累计＋本次金额，并在“关联发票记录”多选字段追加新记录 ID；随后回读两个字段核实。
5. 全部账单更新且回读一致返回 `APPLIED`；主记录建成后有账单失败或回读不一致返回 `PARTIAL`，逐张标明结果，不回滚、不重试。

请求与返回均带 `requestId`、`account`、`contractVersion: 1`。返回固定错误码，NS 原始异常只写入脚本执行日志（标题 `VENDOR_BILL_WRITEBACK_FAILED`）。

## 3. 本系统的状态与人工处理

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 待确认回写预览 | 有账单累计已收与明细合计不一致 | 核对预览中每张账单的写前、本次、写后累计及差额后点“确认回写预览”。写后累计＝写前＋本次，历史差额不变 |
| 待写入 NS | 方案（及预览）已确认 | 写入开关、写入脚本和白名单都满足时可写入，否则页面显示原因 |
| 正在写入 NS | 已加账单锁并发出请求 | 等待结果；超过 10 分钟仍无结果可人工核实 |
| NS 已登记 | NS 返回成功并已回读核实，或人工核实已登记 | 完成。之后审核变化不会改回失效，只提示人工核对 NS |
| NS 已有同号登记 | 写入前查到同号发票记录 | 未写入，由财务核对是否手工登记过 |
| 待处理 | NS 复核不通过（如账单累计已变化）或写入失败但确认未写入 | 按原因处理；累计已变化时点“重新查询账单”后重新确认方案 |
| 部分写入，待核实 | NS 已建发票记录，但账单未全部更新 | 账单锁保留。财务在 NS 补齐后标记“NS 已完整登记” |
| 结果不明，待核实 | 请求已发出但没有得到可核对的结果 | 账单锁保留，不能直接重发。在 NS 核实后标记“已完整登记”或“没有任何写入”；后者才会回到待写入 |

请求未发出（连接失败、认证被拒、写入开关关闭）时任务回到“待写入 NS”，账单锁释放。

## 4. 第一笔验收

1. 用 **YE-DQ20260624-Z010** 相关的真实发票完成整票审核、查询账单并确认方案。此前只读验证返回供应商 **8879**、母单 **308488**、候选 **395762 / VENDBILL35675**；这是历史查询证据，不能当作本次额度或归属结论。
   - 完整审核每条分配，逐行金额与数量完整、当前审核版本有效；不能只依据“每行都有分配”或“开票任务已完成”。
   - 2026-10-29 已移除匹配详情中的“NS 回写准备”提示区域。通过已认证的 `GET /api/writeback/invoices/{id}` 查询未就绪原因；历史已审核发票可通过 `POST /api/writeback/invoices/{id}/recheck` 重新检查，或启用后台补扫。
   - 进入生成的任务 `/writeback/{id}` 查询账单；若子采购精确关联为空，须人工核实实际 NS 子公司、账单归属及各笔分配金额，填写依据后确认方案。查询和方案确认本身不执行 NS 写入。
2. 核对“NS 回写预览”：写前累计、本次金额、写后累计，以及账单是否一致。
3. 部署写入脚本，填写脚本编号，`WRITEBACK_VENDOR_ALLOWLIST` 只填该供应商（如 `8879`），开启 `NETSUITE_WRITE_ENABLED`，重启后端。
4. 在任务详情点“回写到 NS”，确认弹窗后写入。只写这一张，不批量试写。
5. 在 NS 页面逐项核对：新发票记录的名称、开票日期、供应商、明细行；账单“供应商发票金额”是否等于写后累计，“关联发票记录”是否追加了新记录。
   - 账单的“关联发票记录”是多选字段，脚本用 `submitFields` 追加并回读核实；首次写入须确认该字段在 NS 中确实保存。若回读不一致，任务会进入“部分写入”。
   - 同时核对账单上的用户事件脚本（如 `SWC_UE_Hide.js`）是否因本次更新产生额外改动。
6. 核对无误后再逐步增加白名单供应商。试点供应商开始回写后，财务停止在 NS 手工登记该供应商的发票。

不要通过直接改数据库状态绕过检查。

## 5. 边界

- 来源身份不完整、供应商名称不一致、税额缺失或为负、负行、数量换算不完整等会在整票检查中阻断。购买方为空不单独阻止入队；有值且与采购公司规范化名称不一致时仍须核实，不影响其他主体与账单归属校验（2026-10-29 确认）。零税额发票与账单照常登记。
- `classification:*` 不解释为 NS 子公司 ID；需人工核实真实子公司归属。
- 查询额度没有预留；写入时由 NS 端按冻结的写前累计复核，额度被占用时返回“账单累计已变化”。
- 不做 NS 请求账本、业务唯一键和旧网页登记入口协调，不提供自动续做（方案第 1.1 节）。已登记发票的撤销或更正由财务在 NS 处理。

接口与实现见 [模块说明](../backend/modules/writeback/README.md)。代码验证使用隔离测试数据和伪造的 NS 接口；真实写入验收须在 NS 部署脚本后按第 4 节执行。


## 6. 回写搜索范围修复（2026-10-29）

写入 RESTlet 修订号 `2026-10-29.1` 修复 `duplicate_check` 阶段的 `SSS_SEARCH_RESULT_LIMIT_EXCEEDED`：旧版为探测超量直接调用 `getRange({start: 0, end: 1001})`，即使结果为空也超过单次请求上限。新版沿用只读查询脚本的分段方式，每次最多取 1000 条，必要时再单独读取第 1001 条；超过业务上限仍返回 `QUERY_LIMIT`，不截断后继续写入。参见 [Oracle getRange 文档](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_456010986327.html)。

重复检查继续按发票号码、供应商内部 ID 和有效记录过滤；后续账单检查仍按目标账单读取并校验供应商、母采购、审批、作废、额度及写前累计。此修复不改变业务范围。需更新实际写入 RESTlet（本地测试配置为脚本 496）的脚本文件，更新本地文件或重启后端不会替换 NS 中的脚本。

隔离测试覆盖空结果、1/999/1000/1001 条重复记录、1000/1001 条账单核销展开行，及超量时任何记录均未写入。本次未部署 NS，也未重新提交实际回写请求。
