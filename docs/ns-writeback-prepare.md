# NS 回写准备：部署与验证

2026-10-28：阶段 A/B 已实现。当前流程为 **整票审核 → 生成准备任务 → 查询候选账单 → 确认并冻结方案**。NS 发票主记录、明细、账单累计金额仍未写入；没有 execute/apply/recover 入口。

## 部署

1. 停止旧后端，保留 `.env` 与既有本地配置。运行 `npm.cmd run db:business:upgrade`，确认业务库迁移达到 `0036_writeback_prepare`。此迁移只新增四张 `writeback_*` 表，不删除旧表；已有 0035 迁移继续保留。
2. 配置以下开关与已有只读 RESTlet 编号，重启后端；前端发布使用 `npm.cmd run build`。

```dotenv
WRITEBACK_QUEUE_ENABLED=true
WRITEBACK_QUERY_ENABLED=true
NETSUITE_VENDOR_BILL_QUERY_SCRIPT=486
NETSUITE_VENDOR_BILL_QUERY_DEPLOY=1
NETSUITE_WRITE_ENABLED=false
```

`WRITEBACK_QUEUE_ENABLED` 默认 true，控制新增入队及补扫，关闭后旧任务仍会因审核变化而失效。`WRITEBACK_QUERY_ENABLED` 默认 false，控制后台补扫和只读自动查询；关闭时可在任务详情手工查询以便先做单笔验收。上述查询仍使用现有 NS 认证配置。即使误开通用 `NETSUITE_WRITE_ENABLED`，本阶段也没有写调用。

无需为此阶段再部署写入脚本。已部署的 `vendor_bill_query_restlet.js` 应使用仓库修订 `2026-10-28.3`；RESTlet 外部地址不因文件修订改变。

## 第一笔验收

1. 在匹配详情找到与 **YE-DQ20260624-Z010** 相关的实际发票。先确认发票、子采购和母单已同步；供应商、实际公司、币种与母采购内部 ID 必须明确。
2. 完整审核这张发票的每条分配。不能只依据“每行都有分配”或“开票任务已完成”；金额与数量必须逐行完整，当前审核版本有效。详情的“NS 回写准备”会显示未就绪原因。
3. 历史已审核发票点“重新检查整票”，或启用后台补扫；点击生成的任务进入 `/writeback/{id}`。后台查询或点击“重新查询账单”只执行查询。
4. 核对任务解析出的供应商/母单。此前只读验证使用供应商 **8879**、母单 **308488**，返回候选 **395762 / VENDBILL35675**。这是历史查询证据，**不能直接当作本次额度或归属结论**。
5. 若子采购精确关联为空，填写各审核分配对应账单与金额，核实实际 NS 子公司，并填写依据、勾选确认；可将同一分配拆到多张账单。后端校验每条分配金额守恒和每张账单本次合计。
6. 提交后应显示“方案已确认”，保留确认人、时间与查询证据，同时显示“NS 写入尚未接入”。这不是 NS 登记成功。

发票换版、取消分配或采购依据变化后，任务应为“审核已失效”；刷新后旧版本确认返回 409。不要通过直接改数据库状态绕过检查。

## 边界与下一阶段

- 来源身份不完整、购买方/供应商名称不一致、零税额、负行、数量换算不完整等会在整票检查中阻断，显示原因。
- `classification:*` 不解释为 NS 子公司 ID；需人工核实真实子公司归属。
- 查询额度没有预留，也不核实此前其他系统登记的完整发票主明细。
- 后续阶段 C 还需 NS 请求账本、写前 inspect、持久目标锁、幂等 apply/status/recover、未知结果保护及真实沙箱验收。不能仅开启一个开关就上线写入。

接口与实现边界见 [模块说明](../backend/modules/writeback/README.md)，完整后续方案见 [发票回写方案](ns-invoice-writeback-plan.md)。本次代码验证使用隔离测试数据；真实母单在新队列里的端到端验收应在迁移部署后执行。
