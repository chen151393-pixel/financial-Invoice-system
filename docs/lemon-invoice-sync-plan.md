# 柠檬云进项发票自动拉取接入方案

状态：方案（2026-10-08，v2）。本文只做接口接入与同步链路设计，不修改业务代码、不执行迁移、不发起真实柠檬云调用。与 [导入发票与现有子采购订单匹配方案](lemon-invoice-matching-plan.md) 的关系：那份文档第 0 节描述"本地 XLS 导入"的当前范围，本文补上"发票从哪里来"的自动化通道；匹配、审核、分配规则仍以那份文档为准。

> v2 更正说明：v1 误判 `open2.ningmengyun.com`（记账开放平台）"没有批量列表接口"。经核实，其「发票」模块包含 `POST /api/Invoice/Invoice/GetInvoice`，即**账套进项发票批量列表接口**，正是口径 B（账套已录入进项票）所需的接口。以下结论已据此修正。

## 0. 结论

| # | 结论 | 理由 |
| --- | --- | --- |
| 1 | 生产接入走**柠檬云官方开放平台 REST API**，不用 lemonclaw 命令行工具做生产同步器 | 官方 REST 有标准化认证、版本化契约、可纳入后端常驻进程；lemonclaw 是面向 AI 助手的交互通道，依赖 WorkBuddy 运行时与自动更新，不适合常驻服务 |
| 2 | 口径 B（账套已录入进项票）的主接口 = **`open2` 记账开放平台的 `GetInvoice` 批量列表**；口径 A（税局全量）才是新「财税能力开放平台」三步同步 | 用户已确认口径 B；`GetInvoice` 直接按 `asid` 账套返回已录入进项票，且**不需要税局登录态**，自动化风险最低 |
| 3 | 两个平台是不同的系统，不要混用：`open2`=记账开放平台（老，账套内数据）；`opendocs.nmy.cn`=财税能力开放平台（新，ISV 系统集成，税局同步/开票/查验） | 认证方式、返回结构、取数口径都不同。`GetInvoice` 只在 `open2` 上，不在新平台 |
| 4 | 架构上包一层**数据源适配器**，把"数据从哪来"和"数据怎么入库"拆开 | 拿到凭证前可先用现有通道把入库链路跑通并验证字段映射，拿到凭证后只换适配器，不动业务代码 |
| 5 | 分页以**日期窗口 + 来源记录去重**为主，不依赖全局游标 | `GetInvoice` 用 `page`/`rows` 数字分页，账套内增删票可能导致偏移漂移；按开票日期分月窗口驱动 + 记录级去重更稳。新平台数据查询的游标续传仅适用于口径 A |
| 6 | 口径 B 最大的自动化风险已消除：无需**税局登录态** | 票已在账套内，`GetInvoice` 只是读账套数据。税局登录态风险只存在于口径 A 的税局同步（可能要短信验证码），已降为可选 |

## 1. 两条接入路径的取舍

柠檬云对外有多个入口，先分清哪条对应口径 B：

- **口径 B（已确认）：账套里已录入的进项票** → 来源是 `open2` 记账开放平台的 `POST /api/Invoice/Invoice/GetInvoice`（账套进项发票列表）。这条不需要税局登录，只读账套，最适合做常驻自动拉取。
- **口径 A：税局全量进项票** → 来源是新「财税能力开放平台」`opendocs.nmy.cn` 的"发票数据同步"（三步异步，从企业电子发票服务平台拉取），是账套数据的超集，但需先完成税局登录，可能要短信验证码。

> 你这次给的 `open2protest.ningmengyun.com` 是拼写误差，正确地址是 `open2.ningmengyun.com`（记账开放平台，文档页 `/Home/Introduction`）。它**确实**有批量列表接口 `GetInvoice`，我 v1 说它"只有单张查票 + 生成凭证"是错的——已更正。

| 产品 | 地址 | 定位 | 认证 | 适合本系统 |
| --- | --- | --- | --- | --- |
| 记账开放平台（老） | `open2.ningmengyun.com`（`$ACCAPI_HOST`） | 第三方内嵌／系统集成，记账／进销存／代账接口 | 商务注册第三方应用 → 获取账号授权（已有账号 OAuth）→ `Authorization: Bearer <token>` | **口径 B 主接口（`GetInvoice`）** |
| 财税能力开放平台（新） | `opendocs.nmy.cn`，文档 `opendocs.nmy.cn` | 面向 ISV 的标准化 REST，发票同步／开票／查验／税务登录 | `appId` + `appSecret` → JWT Bearer（`access_token` 2h、`refresh_token` 30d） | **口径 A 可选超集（税局同步）** |
| 阿里云云市场 | `fpkjnmy.market.alicloudapi.com` | 按量付费购买同一批接口 | AppCode / AppKey+AppSecret | 备选采购渠道，适合短期试用 |
| AI 财税开放平台 | `nmy.cn/skills` | 自然语言 Skill 通道 | 柠檬云账号登录 | 人工验证用，不作生产集成 |

> 备注：本系统当前用 lemonclaw 命令行通道拉到的进项发票分页列表，底层是 `nmy.cn` 连接器平台的账套发票查询，与 `open2` 的 `GetInvoice` 是"同源账套数据、不同访问通道"。生产集成应在自己的后端直接调用 `open2` 的 `GetInvoice`（用自己申请的第三方应用凭证），而不是依赖命令行通道常驻。

### 1.1 逐项对比

| 维度 | `open2` GetInvoice（口径 B，主） | 新平台税局同步（口径 A，可选） | 现有 lemonclaw 命令行通道 |
| --- | --- | --- | --- |
| 取数口径 | 账套内已录入进项票 | 税局全量进项票（含未入账） | 账套内已录入进项票 |
| 是否需要税局登录 | 否 | 是（可能要短信验证码） | 否 |
| 调用模式 | 同步，`page`/`rows` 分页 | 异步三步（建任务→查状态→查结果） | 同步（命令行封装） |
| 认证 | 第三方应用 + 已有账号授权 Bearer | appId/appSecret JWT | API Key 在 WorkBuddy 侧 |
| 稳定性 | 官方接口契约 | 官方接口契约 | 随 skill 版本漂移 |
| 可运维性 | 可纳入后端进程 | 可纳入后端进程（需轮询/回调） | 需服务器装 Python 与运行时 |
| 结论 | **目标态（主）** | **可选超集** | **仅过渡验证** |

### 1.2 口径已定：账套已录入的进项票

用户已确认口径 **B：只拉柠檬云账套里已录入的进项票**（即"该账套目前只用于记录进项发票"的那个柠檬云财务账套，`asid` 见同步状态）。

精确来源 = **`open2` 记账开放平台的 `GetInvoice` 账套进项发票列表**（`invoiceCategory=10080` 进项发票，按开票日期范围 + `page`/`rows` 分页）。它正好对应用户已确认的范围，不引入账套外、尚未入账的票，且无需税局登录态。

新平台 `opendocs.nmy.cn` 的"发票数据同步"是账套数据的**超集**（口径 A），可能包含尚未录入账套的票，且依赖税局登录态。它降为"可选补充来源"，不在第一阶段接入。

两者复用同一套适配器与入库逻辑，只是取数入口不同。当前 XLS 导入来源标记为 `excel/lemon-excel`，属于文件导入命名空间，不代表已授权账套（见匹配方案第 0.1 节）；口径 B 下 XLS 导入是否保留，待阶段 4 前再定。

## 2. 官方接口能力清单（口径 B 主链路）

### 2.1 主链路：`GetInvoice` 账套进项发票列表（同步）

| 项 | 内容 |
| --- | --- |
| 请求地址 | `POST $ACCAPI_HOST/api/Invoice/Invoice/GetInvoice`（`$ACCAPI_HOST = https://open2.ningmengyun.com`） |
| 认证 | 请求头 `Authorization: Bearer <token>`（token 由"获取账号授权 → 已有账号"流程取得，绑定到被授权账套 `asid`） |
| 关键入参 | `invoiceCategory=10080`（进项发票）；**开票日期范围**（参数名待从文档确认，如 `kprqStart`/`kprqEnd` 或 `dateS`/`dateE`）；`page`/`rows` 分页 |
| 返回结构 | `State`/`SubState`/`Msg`/`Data`：`State=1000` 成功；`2000` 成功但业务失败；`9999` 调用失败 |
| 是否含明细 | **待确认**：列表是否直接返回商品明细 `details[]`，还是需要按发票代码+号码再调单张明细接口（见 §6 待确认 #2） |

调用示例（Bearer 头取自 open2 文档"开发前必读"示例）：

```
POST https://open2.ningmengyun.com/api/Invoice/Invoice/GetInvoice
Authorization: Bearer <token>
Content-Type: application/json

{
  "invoiceCategory": 10080,
  "kprqStart": "2026-01-01",
  "kprqEnd": "2026-01-31",
  "page": 1,
  "rows": 100
}
```

> 返回 `Data` 内的发票字段以文档/实测为准。公开文档未给出 `GetInvoice` 的完整字段表，v1 中的字段表来自新平台口径 A 样例，**接入前需用 `GetInvoice` 真实响应复核**（见 §6 #2）。

### 2.2 可选超集：新平台"发票数据同步"（三步异步，口径 A）

仅当后续需要"税局全量超集"时才接入。三步：

| 步骤 | 接口 | 关键入参 | 产出 |
| --- | --- | --- | --- |
| 1 发起同步 | `POST /api/v1/open/invoice-sync/create-task` | `uscc`、`areaCode`、取票时间范围 | `taskID` |
| 2 等待完成 | `POST /api/v1/open/invoice-sync/task-status` | `taskID`、`uscc` | 任务状态 |
| 3 查询结果 | `POST /api/v1/open/invoice-sync/data-query` | `uscc`、`jxxbz`、`kpyf`、`page`、`taskID` | 票头 + 明细 |

字段命名提醒：接口历史兼容同时存在 `taskID` 与 `taskId` 两种写法，**以具体接口 schema 为准，不要自动转换大小写**；回调通知里的字段固定为 `taskId`。该链路需先完成税务登录（可能要短信验证码），不适合无人值守的第一阶段。

> 同平台"发票列表数据查询"（`POST /api/v1/open/red-invoice/invoice/list`）容易误当成通用列表。它属于**红字发票开具**模块，只返回"可用于红字冲销的蓝字发票"，**不是通用进项发票列表**，不要接入做批量拉取。

### 2.3 结果字段（v1 口径 A 样例，仅作映射参考，待 §6 #2 复核）

票头：`invoiceID` 记录 ID、`fpdm`/`fphm`/`sdphm` 代码/号码/数电票号、`xfmc`/`xfsbh` 销方、`gfmc`/`gfsbh` 购方、`kprq` 开票日期、`je`/`se`/`jshj` 金额/税额/价税合计、`fplx`/`fpzt` 类型/状态、`jxxbz` 进销项标志（1 进项）。

明细 `details[]`：`mc` 名称、`ggxh` 规格、`jldw` 单位、`sl` 数量、`dj` 单价、`slv` 税率、`je`/`se`/`jshj`、`spbm` 税收分类编码。

特殊票种（机票、铁路、机动车、二手车等）第一期可原样存 JSON，不强行展开。

## 3. 推荐架构

沿用项目既有分层：`integrations` 只放外部系统客户端，业务规则留在业务模块，`sync` 负责任务编排。

```
  触发（手动按钮 / 月度定时）
            │
            ▼
  sync：LemonInvoiceSyncService
  （建任务 → 拉取 → 逐票校验 → 入库 → 记结果）
            │
            ▼
  integrations/lemon：LemonInvoiceSource（抽象接口）
      ├── Open2LemonSource      open2 记账开放平台 GetInvoice（口径 B，目标态）
      └── CliLemonSource        过渡期验证用，不参与生产调度
            │
            ▼
  invoice 模块：invoices / invoice_lines
  （复用现有表、来源去重、来源版本、命名锁）
            │
            ▼
  matching 模块：候选与分配（复用现有台账）
```

模块归属：

| 位置 | 职责 | 不做的事 |
| --- | --- | --- |
| `backend/integrations/lemon/` | 认证、HTTP 调用、分页、字段映射为内部对象 | 不写数据库、不决定业务状态 |
| `backend/modules/sync/` | 任务编排、持久任务台账、失败与续跑 | 不解析发票业务金额规则 |
| `backend/modules/invoice/` | 发票与明细入库、来源去重、来源版本 | 不直接调外部 HTTP |
| `backend/modules/matching/` | 候选推荐与分配确认 | 不读柠檬云 |

关键点：**外部 HTTP 必须在数据库事务之外执行**，每张发票一个短事务原子更新，沿用现有 NS 保存的命名锁与"提交结果不明先核实、不盲目重试"原则（见 `backend/modules/sync/README.md`）。

## 4. 关键设计点

### 4.1 分页与续跑（按日期窗口，不依赖全局游标）

`GetInvoice` 用 `page`/`rows` 数字分页。账套内若在两页之间新增/删除发票，纯偏移分页会漂移或漏票。做法：

- **以开票日期分月窗口驱动**：每次同步锁定一个月份窗口（如 `2026-01-01`~`2026-01-31`），窗口内逐页拉全。
- **窗口重叠兜底**：相邻月份窗口保留少量重叠（如各向前后多扫几天），覆盖"开票日期在上月、录入落在本月"的晚到票。
- **记录级去重兜底**：同一 `(tenant, external_system, external_account, external_record_id)` 重复落入不产生新票，抵消分页漂移。
- 新平台数据查询的游标续传（`invoiceID` 大于某值）仅适用于口径 A，不在第一阶段使用。

### 4.2 任务模型

本地任务台账保存上游标识（`asid`/账套、同步窗口、来源）。口径 A 接入时再追加 `taskID` 与 `uscc`（状态查询、结果查询、回调通知共用同一份幂等记录）。

### 4.3 时间口径与晚到发票

| 口径 | 出现在 | 说明 |
| --- | --- | --- |
| 取数窗口 | 发起 `GetInvoice` | 决定"这次从账套取哪个日期范围的票" |
| 开票日期 `kprq` | 票头字段 | 业务口径，对用户展示 |
| 录入日期 | 账套字段 | 部分票有，用于晚到判断（可选） |

**晚到发票是真实存在的**：开票日期在上个月、但录入/取数落在本月的票，只按当月窗口会漏。月度任务需回扫最近 N 个月（N 由实际到票节奏决定），靠去重避免重复。

### 4.4 来源去重与业务同票识别

沿用匹配方案第 4.3 节原则，两层分开：

- **来源去重**（同一账套反复同步）：唯一键 `tenant_id + external_system + external_account + external_record_id`。
- **业务同票识别**（同一张票从不同渠道进来）：数电票用 `sdphm`，传统票用 `fpdm + fphm`，结合购方主体。不能只按金额、日期或名称去重。

行级唯一键：`tenant_id + invoice_id + source_line_key`。明细行号 `mxxh` 不能直接当主键唯一定位（重排、同名重复行无法无歧义识别），需先验证稳定组合。

### 4.5 金额精度

接口返回金额按**精确字符串**解析为 `Decimal`，不经过浮点；数据库用 `DECIMAL`。展示与计算口径与现有匹配方案第 7.1 节一致。

### 4.6 登录态与任务前置检查

- **口径 B（`GetInvoice`）：无需税局登录态**——票已在账套，只读即可。任务前置只需检查 `Bearer token` 有效性（失效则刷新/提示重新授权）。
- **口径 A（税局同步）：必须先完成税务登录**，可能要人工短信验证码，会话有有效期。若接入，任务第一步检查登录态，失效且需人工验证码时标记"待人工登录"，**不取数、不伪造成功**，界面提示。

## 5. 实施顺序

| 阶段 | 交付 | 前置条件 |
| --- | --- | --- |
| 0 商务与口径 | `open2` 第三方应用凭证 + 已有账号授权流程；确认取数口径（已定 B）；确认账套 `asid` 与 window 策略 | 用户与柠檬云商务 |
| 1 客户端连通 | `integrations/lemon` open2 认证与 `GetInvoice` 调用，单账套只读连通，脱敏字段映射表（以真实响应复核 §6 #2） | 阶段 0 |
| 2 手动同步 | 建任务 → 拉取 → 落库 → 去重 → 查询展示；四类数据状态齐全 | 阶段 1 |
| 3 定时同步 | 月度任务、日期窗口、重叠兜底、失败恢复、token 失效提示 | 阶段 2 验证通过 |
| 4 匹配衔接 | 与 `matching` 模块对接，进入既有候选与分配链路；XLS 导入是否保留在此前定 | 阶段 2 |
| 5（可选）口径 A | 视需要接入新平台税局同步作为超集，含税务登录态处理 | 阶段 3 + 业务确认 |

阶段 2 验收出口与匹配方案第 0.3 节一致：**同步入库 → 刷新后可查 → 明细完整 → 重复同步不增票 → 不同账套不串账**。

## 6. 待确认事项

1. **取数口径**：已确认＝**柠檬云账套已录入的进项票（口径 B）**，主接口＝`open2` `GetInvoice`。XLS 导入是否保留、口径 A 是否作为超集，待阶段 4/5 前再定。
2. **`GetInvoice` 字段（需从你的 open2 文档/实测确认）**：① 开票日期范围参数名（`kprqStart`/`kprqEnd` 还是 `dateS`/`dateE`）；② 列表是否直接返回商品明细 `details[]`，还是需按发票代码+号码再调单张明细接口；③ 账套/`asid` 如何随请求指定（token 已绑定账套，还是需额外传 `asid`）；④ 其他过滤项（`fpdm`/`fphm`/`gfmc`/`xfmc`/`fpzt`）。
3. **`open2` 第三方应用凭证申请**：联系柠檬云商务注册第三方应用 → 走"获取账号授权 → 已有账号"流程让上海绎视数码科技有限公司授权 → 取得 `Bearer token`。这是口径 B 接入的硬前置（与 lemonclaw 命令行通道的凭证不是同一套）。
4. **历史回溯范围**：首次全量同步往回拉多久（建议按匹配业务需要的历史基线上限）。
5. **是否接口径 A**：视业务是否需要"税局全量超集"；若接，需评估税务登录态（短信验证码）对无人值守的影响。
