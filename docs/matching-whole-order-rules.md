# 发票与子采购单整单匹配规则

状态：2026-10-30 已实施（与方案的出入见各节“实施说明”）；SQLite 测试通过，MySQL 并发专项与浏览器验收未执行。归属 `matching` 模块，结束差额沿用 `task` 已有的“按差异结束”。2026-10-30 依据业务确认整理：财务王萍说明供应商一般每月只开一张子采购单；同一母单下的多张子采购单按通知月份分别开票。本文替代 [matching README](../backend/modules/matching/README.md) 中“部分开票”“分次收票”的相关规则；已确认的历史分配不受影响。

## 1. 业务事实与已确认的决定

- 子采购单是开票的最小单位：每张子采购单在其通知开票的月份一次开完，不拆开、不分月开。
- 一张子采购单有几个品名，发票就开对应的几个品名。
- **一票多单：允许。** 同月通知的多张子采购单，供应商可以合并开在一张发票上，按合计整体比对。（用户 2026-10-30 确认）
- **一单多票：不允许。** 一张子采购单只能关联一张发票；发票开得少，按差异结束，不能再关联另一张发票。（用户 2026-10-30 确认）

## 2. 匹配单位

一次匹配 = **整张发票 ↔ 一张或多张完整子采购单**。

- 发票的每一行都必须对应到所选子采购单；所选子采购单的每条有效明细都必须被覆盖。不能只匹配发票的一部分，也不能只选子采购单的一部分明细。
- 一张子采购单在任意时刻最多只有一条有效关联（待审核或已确认）。
- 不再有“剩余应开”的概念，也不再逐张扣减：确认后，子采购单全部明细结束开票。

## 3. 品名对应

1. 发票品名先去掉开头的税收分类（如 `*纺织专用设备*迷你烫画机` 取 `迷你烫画机`），子采购明细取报关品名（为空时取商品名）。
2. 两边按品名分组，同一品名有多行时数量、金额先合计，例如很多张相纸按总数开在一行。
3. 两边的品名集合必须一一对应：发票有、子采购单没有的品名，或者反过来，都判品名不一致。
4. 同一品名两边单位要相同（按单位字典名称）；单位不同判不一致，靠审核说明给出数量口径，不做自动换算。

实施说明：沿用现有 `order_parts` 的综合得分定位——每条子采购明细对应得分最高的发票行（发票只有一行时全部对应该行），再按发票行比对其对应明细的合计；品名多一个或少一个体现为该行“品名不一致”和数量、金额差异，没有另建品名集合比较。最高分并列时不猜配，转人工。

## 4. 比对项（整单口径）

| 比对项 | 规则 | 结果 |
| --- | --- | --- |
| 子采购单号 | 发票备注命中所选子单或其母单 | 一致／不一致（未命中） |
| 销售方与供应商 | 沿用现有供应商模糊规则 | 一致／部分一致／不一致 |
| 购买方与采购公司 | 柠檬云 API 票取账套名称 | 一致／不一致／未提供 |
| 品名 | 第 3 节的品名集合一一对应 | 一致／不一致 |
| 单位 | 每个品名两边单位相同 | 一致／不一致 |
| 数量 | 每个品名的数量合计相等 | 一致／不一致（发票多/少 X） |
| 合计金额 | 整票价税合计对所选子采购单含税合计，容差 0.01 元 | 一致／不一致（发票多/少 X） |
| 税额 | 沿用现有按税率计算，容差 0.05 元；税率未同步显示“未校验” | 一致／不一致／未校验 |

数量和金额**取消“分次收票”**：发票少于子采购单就是不一致。现有的 `check_label_policy` 只用于历史逐行分配的展示。

## 5. 建议与审核

- **先票后任务**（2026-10-30）：财务审核生成任务或任务后继后，系统在同一事务内按单号/供应商召回已有正常且明细完整的发票，复用整单规则自动生成或更新待审建议；按游标分批扫描，不漏掉旧票。含已确认关联的发票跳过。没有唯一方案时转人工，不自动确认；保存失败时审核与任务一起回滚。实现与边界见 [matching 说明](../backend/modules/matching/README.md#任务生成后自动匹配已有发票2026-10-30)。

- **自动建议**：组合必须覆盖整张发票全部行。一张或多张子采购单合计与发票各行**恰好相等**的唯一组合（一票多单），以及**单张子采购单覆盖整张发票**但数量或金额有差异（发票多或少）的候选，一起按置信度比较，默认生成最高分方案；最高分并列不建议。不再按单行拆出部分组合。
  - 实施说明：方案原写“只在全部比对项一致时生成”。实施时保留 2026-10-29 已上线的“置信度优先、有差异也生成待审核建议”规则，差异项在审核时要求填写说明，未改为只建议完全一致。
- **人工关联**：在所选发票行下选择一张子采购单，后端按第 3 节把整单明细对应到发票各行，记账数量和金额由后端生成（`ManualOrderBody` 不再有 `lines`），**不能改小或填 0**。可以关联有差异的子采购单，但必须填写说明；对应的发票行有待审核建议时须先驳回。
- **审核**：整组一起通过或驳回，沿用现有分组审核接口与事务。
- **不能通过**（在原有规则上增加）：子采购单任一明细已有收票、待复核占用或已结束（`ONE_INVOICE`：一张子采购单只能由一张发票开具）。整单建议视图同时显示该原因。

## 6. 差额如何落账

分配仍按子采购明细逐条记录（task 按行计算收票进度），记录的数量和金额来自发票（`order_group_policy.fit`）：

1. 对应同一发票行的明细按顺序记账，每条记到 min(整单应开, 发票该行剩余)；发票等于或多于子采购单时每条记满应开。
2. 发票少时，后面的明细可能记 0（保存为数量、金额都为 0 的分配，表示这条明细本票未开）。
3. 每条分配在 `checks.orderShare` 保存整单应开快照；比对按整单应开计算，不按压缩后的记账数。
4. 确认时，记账少于整单应开的明细由 matching 在同一事务发布 `LinesClosedByDifference`，task 订阅后追加 `difference_closed` 事件并按差异结束，原因即审核说明；任一明细依据已变化或有待复核占用时整个确认回滚。
5. 发票多时子采购明细记满应开，不标超开；发票多出的部分留在发票行可用量里，比对项显示“发票多 X”并要求说明。
6. 一票多单人工关联时，按发票行扣除其他已确认分配后的剩余量记账。

## 8. 历史数据

- 已确认的部分开票分配保持不动，展示仍用“分次收票”说明。
- 已部分开票、还有剩余应开的子采购单，规则上线后不能再关联新的发票。需要人工按差异结束，或者先取消原关联再整单重新关联。上线前先统计这类子采购单的数量。
- 待审核的旧建议：缺少整单分组或整单应开快照时，详情与队列按当前完整子采购单预览差额，关闭通过能力并提示“重新生成建议”；无法完整对应时不沿用旧的一致结论。单条、整组和批量审核接口均校验，不能用旧页面绕过。
- 点“重新生成建议”后，在同一事务内驳回旧待审建议并追加新整单建议，保留旧快照、操作者、时间及升级原因；没有新候选也退出旧待审建议，写入失败则全部回滚。已确认历史不改写，读取页面和导入事件不自动迁移，无需数据库结构迁移。
- 相关实现：`pending_order_policy.py`、`pending_order_service.py`、`matching_query_service.py`、`allocation_service.py`、`group_view_service.py`、`proposal_service.py`；回归见 `test_matching_legacy_pending.py`。

## 9. 验收与验证

已用 SQLite 隔离测试覆盖（`test_matching_manual_order.py`、`test_matching_whole_order_rules.py`、`test_matching.py`、`test_matching_order_priority.py`、`test_ledger_versions.py`）：

- 一票一单完全相等自动建议并整组通过；一票多单合计相等的组合规划。
- 发票少：自动建议与人工关联都要求说明，确认后两条明细按差异结束、各追加一条 `difference_closed`，重复提交不重复结束。
- 发票多：记满应开、要求说明、不按差异结束。
- 已开具（含按差异结束）的子采购单不再出现在候选里，直接提交返回 `ONE_INVOICE`；旧逐行分配已收票的子采购单，整单建议不能通过。
