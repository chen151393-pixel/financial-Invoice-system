# NS 供应商账单回写方案

状态：**待评审（2026-10-27 起草；同日完成第 0 期只读统计，账单对应规则据此改为以母单为主）**。对应[上线计划](launch-plan-2026-11.md)任务 17。依据是用户提供的 `供应商发票平台 (2).zip`（SHA-256：`d98ab6185ba57164d76f2b32f5bc7a9c8e0421eb56aeaf43cf2679871cc1c310`）、NS 正式账套的只读统计和本仓库当前代码。2026-09-13 对上一版压缩包的核对见[保存对象与角色权限](netsuite-vendor-invoice-permissions.md)，本文不重复其中的权限清单。

- 源码部分只做阅读和 `node --check` 语法检查。
- 第 0 期统计只对 NS 正式账套执行 SuiteQL 只读查询（结果见第 2.4 节），未修改 NS 数据、脚本或部署。

## 1. 结论

- **回写目标**：沿用 NS 现有“供应商开票平台”的数据结构（2026-10-28 确认）。
  - 只回写三项业务内容：发票号码（主记录 `name`）、开票日期（`custrecord_swc_vi_billdate`）、开票金额（每张账单一条明细的“本次收”`custrecord_swc_cid_current_amount`）。不改账单单据日期。
  - 每张发票建一条 `customrecord_swc_vendor_invoice`，带对应账单的明细行；明细的母单照常填写，子单字段留空，与现有大多数手工登记一致。
  - 同时更新供应商账单 `vendorbill` 上的两个字段：累计已收票金额 `custbody_swc_vendor_amount`、关联发票记录 `custbody_swc_bill_vendor_num`。
  - 这样财务现有的 NS 查询、报表，以及在 NS 里手工修改、删除发票记录的联动脚本都继续有效。
- **不直接调用现有页面和计划脚本**：它们是给人操作的界面，没有幂等，会吞掉错误，并且存在已知的金额覆盖问题（见第 2.3 节）。
- **改由本仓库新增一个 RESTlet**，在 NS 端完成以下工作：
  1. 重新校验余额和归属；
  2. 用“发票号码 + 供应商”防重复；
  3. 写入发票记录与明细；
  4. 按明细重算账单累计金额。
- **账单以母单为主查找（2026-10-27 第 0 期统计后修正）**：
  - NS 账单从 2026-04 起不再填写子采购单字段 `custbody_swc_bill_created_subpo`，只能通过账单的“创建自”（母单）找到（见第 2.4 节）；
  - 母单下只有一张有效账单时自动对应，约占 93% 的母单；有多张账单且缺少子单字段时，由财务按账单分配金额（规则见第 3.3 节）；
  - 同步时按母单读取并保存账单 ID，页面可见“已生成账单／账单未生成”；
  - 回写成功后，RESTlet 再返回每张账单的 ID、新建的 NS 发票记录 ID 和更新后的累计金额，系统逐张记录。
- **审核通过即触发回写（2026-10-27 确认方向）**：
  - 一张发票的全部分配在比对审核中通过后，系统自动生成回写项，由后台排队写入 NS，不再另设“预览 → 确认”步骤；
  - 审核通过这一步就是人工确认。审核时记下的回写内容不可变，执行前在 NS 端重新校验，内容有变化就停下，等待重新审核。
- **系统端恢复 `writeback` 模块**，保留 AGENTS 第九节要求的保护：写入开关、不可变的回写内容、目标锁、审计、结果不明不重试。
- **分期上线**：
  - 11 月试用期先做**账单 ID 同步与只读对照**：财务仍在 NS 手工登记，系统只标出“已登记／未登记／金额不一致”；
  - 稳定后打开写入开关，**审核通过即回写**。先限定少数供应商，跑通后全量，并约定切换日，停止 NS 手工登记。

### 2.2 数据结构

| 业务含义                              | 记录                                              | 字段                                                                                                                    |
| ------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 发票号码 / 开票日期 / 供应商          | 发票主记录 `customrecord_swc_vendor_invoice`      | `name` / `custrecord_swc_vi_billdate` / `custrecord_swc_vi_vendor`                                                      |
| 明细子列表                            | 发票明细 `customrecord_swc_vendor_invoice_detail` | `recmachcustrecord_swc_vid_main`                                                                                        |
| 账单 / 母采购单 / 子采购单            | 发票明细                                          | `custrecord_swc_vid_bill` / `custrecord_swc_vid_po` / `custrecord_swc_vid_subpo`                                        |
| 应收、此前已收（快照） / 本次收       | 发票明细                                          | `custrecord_swc_vid_billamount`、`custrecord_swc_vid_billpaied` / `custrecord_swc_cid_current_amount`（前缀确为 `cid`） |
| 累计已收票金额 / 关联发票记录 ID 列表 | 供应商账单                                        | `custbody_swc_vendor_amount` / `custbody_swc_bill_vendor_num`                                                           |
| 账单所属子采购单                      | 供应商账单                                        | `custbody_swc_bill_created_subpo`                                                                                       |

“本次可收”的计算在 `VendorInvoice.js` 的 `handleJson`，只计算有税额的账单：

- 账单应收 = 剩余金额 + 非贷项的核销金额。也就是账单总额扣除供应商贷项，已付款部分仍算应收。
- 本次可收 = 应收 − 累计已收票金额。

### 2.3 现有保存链路的问题（与上一版核对结论相同，仍然存在）

1. **语法错误**：`SWC_SS_VendorInvoice.js:55` 的 `split('\x')` 仍无法通过 `node --check`，需要核实 NS 现网文件是否是另一个版本。
2. **没有幂等**：同一批提交两次，会生成两条发票记录，账单金额也会算两次。
3. **金额覆盖**：账单累计金额按页面打开时的“已收”快照加本次金额后直接覆盖。两批并发提交，或同一账单在两个分组中出现时，后写入的会覆盖先写入的。
4. **没有整体回滚**：先建全部发票，再逐个改账单。中途失败会留下“发票已建、账单未改”。页面还吞掉了任务提交异常。
5. **只在浏览器校验**：超额、归属、重复行的检查只在浏览器端，服务端没有复核。
6. **按行号比较**：`SWC_UE_Hide.js` 按行号比较新旧金额，明细行增删后可能错位。

这些问题影响的是人工页面。本方案不依赖这条链路，但第 4 节的 RESTlet 必须避免同样的问题。

### 3.1 账单 ID 怎么拿到

- **同步时读取**：在 `backend/integrations/netsuite/relation_sources.py` 增加一种 SuiteQL 查询，按母采购单 ID 读取“创建自”等于它的供应商账单。
  - 读取内容：账单 ID、编号、供应商、母采购单、子单字段（可能为空）、子公司、币种、审批状态、总额、税额。
  - 不能复用 `getData` 定位账单：它会跳过税额为 0、可收为 0 和 2025-07-01 以前的账单，“查不到”无法区分“未生成”和“已登记满”。
- **保存位置**：账单属于 NS 来源数据，归 `source` 模块。新表 `source_vendor_bills`，只存 ID，不建跨模块外键。由 `source.public` 提供“按母单查账单”。
- **只用于判断和展示**：同步保存的账单金额不用于回写校验。余额和累计金额以回写时 NS 端实时读取的值为准，因为账单在两次同步之间可能已被付款、贷项或手工登记改动。
- **账单生成晚于审核**：审核通过时如果母单还没有账单，回写项停在“等待账单”。之后同步发现账单，系统会自动重新校验并继续回写，不需要重新审核。
- **只读查询 RESTlet（2026-10-28 已实现，未部署）**：在用户原有“供应商 ID + 母单号”查询脚本的基础上，改为 [`netsuite/vendor_bill_query_restlet.js`](../netsuite/vendor_bill_query_restlet.js)：按母单内部 ID 返回全部账单（含已登记满和税额为 0 的），带回子单字段、审批状态、额度和明细合计，不再依赖 `getData`。接口说明见[按母单查询供应商账单](ns-vendor-bill-query-api.md)。它的结果不是回写任务号，也不是写入授权。

### 3.2 回写单位与条件

回写单位：**一张发票一次回写**，与 NS 一条发票记录对应。

一张发票可以分到多个子采购单、多个母单，也就会有多行明细。生成回写项时，系统端先检查以下条件，任何一条不满足就不进入写入队列，并显示原因：

- 发票有效：不是作废、红冲，也不是待复核；
- 该发票的全部分配都已通过且有效，不存在待审核的建议；
- 分配涉及的每个子单都已关联母单（`parent_relation_status = linked`）；
- 每个母单都已按第 3.3 节确定账单与金额；
- 币种一致：账单币种与发票币种相同，不做换算；
- 子公司一致：账单子公司与发票购买方是同一家公司；
- 金额不超过 NS 账单当前的“本次可收”。

只要有一个母单未确定，整张发票就等待，不做部分写入：先写一部分会在 NS 留下这张发票的记录，之后补写会触发防重复冲突或改动已有记录。

### 3.3 账单对应规则（以母单为主）

1. **汇总**：取发票的全部有效分配，经子采购行找到子单、再找到母单，按“母单 × 子单”汇总含税金额。每个子单金额必须正好两位小数，各子单合计等于发票价税合计；超出两位小数时拦下并说明，不自动四舍五入。
2. **查账单**：按母单 NS 内部 ID 读取它的全部账单。“有效账单”指：已批准、未作废，供应商、子公司、币种与发票一致，本次可收大于 0。税额为 0 的账单是否参与，待业务确认（第 7 节问题 9）。
3. **逐母单判定**：

   | 母单情况                     | 处理                                                                                         |
   | ---------------------------- | -------------------------------------------------------------------------------------------- |
   | 只有 1 张有效账单            | **自动对应**：该母单下各子单的金额都记到这张账单；账单有子单字段时，必须是本次分配的子单之一 |
   | 多张有效账单，且都有子单字段 | **自动对应**：按子单字段对应（主要是 2025-11 至 2026-03 的账单）                             |
   | 多张有效账单，缺少子单字段   | **待分配账单**：由财务逐张账单填写金额，每张不超过本次可收，合计等于该母单的分配金额         |
   | 没有账单                     | **等待账单**：之后同步发现账单再自动继续                                                     |
   | 有效账单可收合计小于分配金额 | **额度不足**：阻塞，不自动拆分或调整                                                         |
   | 只有待审批、已拒绝的账单     | **阻塞**：显示原因，等账单审批后自动重新判定                                                 |
   | 只有已登记满的账单           | 查该发票是否已在 NS 登记：已登记标“冲突”，否则标“额度不足”                                   |

4. **冻结**：确定后的“账单 → 金额”随回写项冻结，并记下当时的已收金额作为 `expectedBefore`。财务的分配是审核之后的第二次确认，同样不可修改；分配错了只能作废该回写项后重新生成。

按第 2.4 节的统计，2026-04 以来有子单的母单中，只有一张账单的约占 93%（1227 个），需要财务分配的约 7%（88 个）。已确认不恢复账单上的子单字段（第 7 节问题 8），这部分由财务在系统里分配。

## 4. NS 端：新增回写 RESTlet

新增文件 `netsuite/vendor_bill_writeback_restlet.js`。它与现有的 `finance_source_restlet.js`、`declaration_documents_restlet.js` 相同：放在本仓库，用本地伪造对象做单元测试，由 NS 管理员部署。

### 4.1 只读动作 `inspect`

入参：供应商 ID 加母采购单 ID 列表，或发票号码 + 供应商；也支持按账单 ID 列表读取，用于写入后核实和结果不明时核查。按母单返回：

- 账单列表：ID、编号、子单字段（可能为空）、子公司、审批状态、是否作废、币种、总额、税额、剩余金额、贷项、累计已收票金额、本次可收（计算方法与 `VendorInvoice.js` 相同，但用精确小数，并且不跳过税额为 0 或可收为 0 的账单）；
- 账单上已关联的发票记录：发票号码、开票日期、本次收金额；
- 同一“发票号码 + 供应商”是否已登记过；
- 账单累计金额与明细合计是否一致。

第一期的“只读对照”只用这个动作。

已实现部分：按母单查询账单（账单列表与明细合计是否一致）已作为独立的只读 RESTlet 完成，见第 3.1 节。按账单 ID 读取、已关联的发票记录、“发票号码 + 供应商”查重尚未实现，随写入 RESTlet 一起补充。

### 4.2 写入动作 `apply`

入参：

- `requestId`（系统回写批次项 ID）；
- 发票号码、开票日期、供应商 ID；
- 明细行列表：每行含账单 ID、母单 ID、子单 ID（账单有子单字段时填写）、本次金额（十进制字符串）；
- 每张账单回写前的累计金额 `expectedBefore`。

处理顺序：

1. **防重复**：按“发票号码 + 供应商”查找已有发票记录，判断规则如下。

   | 已有记录                                                       | 返回                           | 是否写入   |
   | -------------------------------------------------------------- | ------------------------------ | ---------- |
   | 没有                                                           | 继续第 2 步                    | —          |
   | 有，且带同一个 `requestId`，账单金额也已更新                   | `already_applied`，附原记录 ID | 不写入     |
   | 有，且带同一个 `requestId`，但账单金额还没更新（上次中途失败） | 补做第 4 步                    | 只更新账单 |
   | 有，但不是本系统写的（财务手工登记）                           | `conflict`，附已有记录         | 不写入     |

   要可靠识别“是不是本系统写的”，建议在发票主记录上新增一个文本字段（例如 `custrecord_swc_vi_platform_request`）保存 `requestId`。没有这个字段时，“同一发票号码 + 供应商”一律按 `conflict` 处理，由人工核对。

2. **复核**：在 NS 端重新读取每张账单，检查：
   - 账单供应商与入参一致，已批准、未作废；
   - 账单的“创建自”（母单）与入参一致；账单有子单字段时，子单也须一致；
   - 账单当前累计金额等于 `expectedBefore`，否则返回 `stale`（系统处理见第 5.1 节）；
   - 本次金额 > 0，且不超过本次可收；
   - 同一请求内的同一账单已合并成一行。

   任何一项不通过就整单返回原因，不写入任何记录。

3. **建发票**：一次保存创建主记录和全部明细。明细的“应收”和“此前已收”写入第 2 步重新读到的值，而不是页面快照。
4. **更新账单**：用 `submitFields` 把累计金额设为“该账单全部有效明细的本次收合计”，并把新记录 ID 追加到关联列表。按明细重算而不是累加，所以重试或补做时结果不会重复。
   - 第 0 期统计有 106 张账单的累计金额与明细合计不一致（见第 2.4 节），对它们重算会顺带改掉历史金额。
   - 因此第 2 步复核时增加一项：本次涉及的账单，写入前累计金额必须等于现有明细合计；不一致时整单返回 `mismatch`，不写入，由财务先在 NS 更正（第 7 节问题 6）。
5. **返回结果**：按账单逐张返回：账单 ID、账单编号、本次金额、更新前与更新后的累计金额、结果；同时返回新建的 NS 发票记录 ID。系统把这些记录到回写项上，在发票详情显示“已登记到哪些账单”。第 4 步部分失败时返回 `partial`，说明哪些账单未更新；系统再用同一 `requestId` 调用，只补做第 4 步。

### 4.3 与现有脚本的配合

- 新建发票记录触发的是 `create` 事件，而 `SWC_UE_Hide.js` 只处理 `edit`，所以不会重复累计。需要在 NS 核实该脚本部署对 RESTlet 上下文是否生效。
- 财务之后在 NS 页面修改或删除本系统写入的发票时，`SWC_UE_Hide.js`、`SWC_UE_DeleteRec.js` 照常联动。系统下一次 `inspect` 时会发现差异，并标为“NS 已改动”。
- 不调用 `SWC_SS_VendorInvoice.js`，也不发它那封固定发件人的邮件。
- 额度：RESTlet 每次调用有 5000 单位上限，而第 0 期统计中单张发票最多涉及 53 张账单。主记录和全部明细必须在第一次调用里一次保存；账单更新超出额度时返回 `partial`，系统用同一 `requestId` 继续补做。每次能处理多少张账单，在 NS 实测脚本单位消耗后确定。

## 5. 系统端：审核通过触发回写

### 5.1 触发流程

```text
比对审核通过（matching，审核事务内）
  └─ 发布事件 AllocationApproved（发票 ID、分配 ID、操作者）
       └─ writeback 订阅（同一事务内）：
            该发票的全部分配都已通过且有效？
              否 → 不处理，等最后一条分配通过
              是 → 生成回写项，冻结回写内容（发票、按“母单 × 子单”汇总的金额）与内容摘要，状态“排队”
后台回写线程（事务外调用 NS，参照 task 的 contract_worker）
  ├─ inspect：按母单读取账单、实时余额与已登记情况（写入开关关闭时也执行，用于只读对照）
  ├─ 按第 3.3 节逐母单判定账单
  │    ├─ 全部自动确定 → 冻结“账单 → 金额”与 expectedBefore
  │    ├─ 需要财务分配 → 状态“待分配账单”，分配保存后冻结
  │    └─ 没有账单、额度不足、账单未审批 → 等待或阻塞，显示原因
  ├─ 写入开关关闭 → 停在“排队”，不调用 apply
  ├─ 系统端重新核对：回写内容摘要未变化、账单仍属于该母单
  ├─ apply：带 requestId 与 expectedBefore 写入
  ├─ inspect：按账单 ID 核实写入结果
  └─ 短事务记录结果：NS 发票记录 ID、逐张账单 ID 与累计金额
```

- **两种“变化”分开处理**：
  - 审核内容变了（发票版本、分配、子采购依据有变化）：回写项转“已过期”，需要重新审核。
  - 只是 NS 余额变了（例如同一账单先写入了另一张发票，`apply` 返回 `stale`）：系统自动重新 `inspect`，额度仍够就更新 `expectedBefore` 后继续写入，不够才转“额度不足”。一个子单被多张发票分配时，这种情况很常见，不能都要求重新审核。
- **加锁顺序**：一张发票涉及多张账单时，按账单 ID 排序后依次加锁，避免两张发票交叉加锁。

- **触发点**：在 `matching` 审核通过（`approval_service.approve`）的事务里发布新事件 `AllocationApproved`，契约写在 `matching.public`。现有的 `AllocationChanged` 按子采购行汇总、不带发票 ID，供任务进度使用，不改它的含义。订阅关系在 `app.py` 登记。
- **审核通过就是人工确认**：不再另设预览和确认页面。回写项在生成时冻结内容与摘要，之后不可修改。执行前，如果发票版本、分配或子采购依据有变化，回写项转为“已过期”，需要重新审核。
- **不在审核请求里调用 NS**：审核事务只登记回写项。NS 调用由后台线程在事务外完成（AGENTS 第三节：外部调用不放在数据库事务内）。审核接口的响应不等 NS 结果，页面另外显示回写状态。
- **重新触发**：分配被取消后再次通过，或回写项过期后重新审核，都会生成新的回写项；旧的回写项保留，用于审计。

- 后端：覆盖以下情况：
  - 审核通过触发：最后一条分配通过才生成回写项、内容冻结与摘要、过期转“已过期”、等待账单后自动继续；
  - 第 3.3 节的每种母单情况：一张账单自动对应、多子单一账单、按子单字段对应、待分配账单与分配校验、额度不足、只有未审批账单；
  - NS 余额变化时自动重新核对，不转“已过期”；
  - 写入开关关闭时只排队、白名单；
  - 目标锁并发、`unknown` 禁止重发、写入开关；
  - 事件订阅。

  涉及并发的部分要在 MySQL 上验证，不能只靠 SQLite 测试。

- 联调：上线只对接 NS 正式账套。第 2 期首次写入前，先选定一个白名单供应商的少量发票，审核通过后逐张写入，并逐张对照 NS 页面；不批量试写。
